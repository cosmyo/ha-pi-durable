# Installation and configuration (experimental 0.2.0)

Use an **authorized test Home Assistant OS installation**, an administrator account and a backup/rollback plan. Supported architectures: **amd64** and **aarch64**. This is an experimental community App, not an official HA/Pi product. The App itself is not a HACS package or a Devices & services integration; the optional [Hearth Assist](#hearth-assist-voice) voice link adds a small integration that you install through HACS. Container/Core installations without Supervisor cannot install it. See [validation](../docs/validation.md) for actual evidence—not a blanket compatibility claim.

## Add the repository and install

[![Add Hearth Pi's repository to Home Assistant](https://my.home-assistant.io/badges/supervisor_add_addon_repository.svg)](https://my.home-assistant.io/redirect/supervisor_add_addon_repository/?repository_url=https%3A%2F%2Fgithub.com%2Fcosmyo%2Fha-pi-durable)

1. Click the button, enter/select your HA instance URL and confirm **Add**. The official My Home Assistant page only opens the repository dialog; you still review and install the App yourself.
2. Alternatively, open **Settings → Apps → Install app** (App store), select **⋮ → Repositories**, add `https://github.com/cosmyo/ha-pi-durable` and select **Add**.
3. Find **Hearth Pi** in the new repository card, open it and select **Install**. The preview is built on your HA host; allow several minutes and check the App/Supervisor logs if installation fails. No manual Git, Node, SSH or Docker setup is required for Home mode.
4. Open the App's **Configuration** tab and complete the following options **before starting**. Older HA versions call Apps **Add-ons** and Install app **Add-on store**.

A developer/local build is also possible by copying the complete `hearth_pi/` directory to `/addons/hearth_pi`; it is not needed for the App-store path.

## Configure before starting

1. Enable **Advanced mode** in your HA profile if needed. Go to **Settings → People → Users**, open your trusted administrator user and copy its **ID**. This is the HA user ID, not a person entity or a token.
2. Set `public_origin` to the **exact HTTPS origin used to open HA**, e.g. `https://home.example`: no path or trailing slash. This preview requires HTTPS Ingress (such as an existing HA Cloud or HTTPS reverse-proxy URL); plain HTTP LAN access is not a supported alternative. The My Home Assistant instance URL should use this same origin.
3. Choose the provider and list the exact entities Hearth may read. Copy IDs from **Settings → Devices & services → Entities**. The example `sun.sun` is optional and only works if that entity exists on your instance. Remove it or replace it with your intended scope. Empty means deny all; there is no wildcard/domain-wide grant.

Example for subscription login; replace both placeholders:

```yaml
authorized_user_ids:
  - REPLACE_WITH_YOUR_HA_USER_ID
service_actions_enabled: false
allowed_services: []
allowed_entities:
  - sun.sun
public_origin: "https://home.example"
provider: openai-codex
model: ""
openai_api_key: ""
workspace_enabled: false
workspace_owner_ids: []
access_mode: scoped
risk_judge_model: auto
risk_judge_url: ""
risk_judge_api_key: ""
risk_judge_timeout_ms: 15000
risk_judge_session_ttl_ms: 300000
briefing_summary_model: auto
approval_notifications: false
member_user_ids: []
guest_user_ids: []
trusted_user_ids: []
assist_enabled: false
assist_satellites: []
```

Select `provider: offline` instead to test startup without AI credentials; its replies are synthetic, not model inference. Do **not** create or paste an HA long-lived access token: the App gets its server-side HA API credential from Supervisor. Never put provider credentials or login redirect URLs in chat or issue reports.

4. Save, open the **Info** tab and select **Start**. Enable **Start on boot** and **Show in sidebar** if desired, then select **Open Web UI**. Refresh the HA browser if the sidebar entry has not appeared. The sidebar entry is visible to every Home Assistant user; only users in `authorized_user_ids` can use Hearth (everyone else gets an authorization error).
5. For subscription mode, open **Settings → Account** from the sidebar drawer (or the ☰ menu on phones) and complete sign-in below. Create a **Home** session and ask about an entity you allowed. **Code** sessions intentionally have no HA tools. Changing App options requires restarting **only Hearth Pi**, not HA Core.

## Optional Code mode

Leave `workspace_enabled: false` for the normal App-store installation. The sidebar/App installation does **not** provision the isolated coding worker. Code mode requires the separate trusted-operator setup in the [workspace guide](../docs/workspace.md), named workspace owners and its own backups. There is no one-click Code-worker installation in this preview; do not enable it without the worker or relax its confinement.

**Who may use Code sessions.** With `workspace_owner_ids: []` (the default) the original rule applies: `workspace_enabled: true` needs exactly one entry in `authorized_user_ids`, and that owner is the workspace owner. A household with two or more authorized owners lists who may code instead, for example:

```yaml
authorized_user_ids:
  - REPLACE_WITH_FIRST_HA_USER_ID
  - REPLACE_WITH_SECOND_HA_USER_ID
workspace_enabled: true
workspace_owner_ids:
  - REPLACE_WITH_FIRST_HA_USER_ID
```

Each listed ID must also be in `authorized_user_ids` (at most 5). Only listed owners see the **Code** button and their Code sessions; every other authorized owner keeps Home sessions only, and the server refuses their Code requests with `workspace_not_allowed`. Removing someone from the list hides their earlier Code sessions without deleting them. All listed owners share one workspace volume and its files, so list only people who trust each other with them.

If Hearth does not start after a configuration change, the App log names the problem without any option value, for example `Hearth Pi could not start: invalid configuration: workspace_requires_one_trusted_owner` (a second owner was added while `workspace_owner_ids` is empty), `workspace_owner_not_authorized` (a listed ID is not in `authorized_user_ids`) or `invalid_workspace_owner_ids` (more than 5 entries or a malformed ID).

## Navigation (unreleased source slice)

The sidebar drawer keeps three rows below your conversations: **Today** (a badge counts unread cards), **Apps**, and **Settings** (a compact status line, e.g. "Full access · ChatGPT ✓ · Claude ✓"). **Settings** opens one sheet with grouped list rows, iOS-Settings style: **You** (personal name/tone/language and default model, at the top), **Home permissions** (current mode), **Account** (provider sign-in status), **Briefings & watchers**, **Memory**, **Insights**, **Home World**, and **About** (app version, "Independent community app · Pi Durable is experimental", and the configured inference provider). Each row opens the same dialog it always has — only the entry point moved, not what it does or its id. The permission badge next to the conversation title still opens **Home permissions** directly, without going through Settings.

## Troubleshooting first startup

- **Repository not visible:** refresh the App store/browser; inspect **Settings → System → Logs → Supervisor** for repository/build errors. Check your architecture and Internet access.
- **No sidebar entry:** enable **Show in sidebar** on the App's Info tab, use an administrator account and refresh HA. **Open Web UI** is the direct alternative.
- **Access denied:** check `authorized_user_ids` and the HTTPS origin; sidebar visibility alone does not authorize you. Do not disable authentication or paste tokens to bypass it.
- **No HA entities:** check `allowed_entities`, save/restart Hearth and use a **Home** session. The default is intentionally empty. Reads need no service-action permissions; keep those disabled while testing.
- **Cannot send a prompt:** check the configured provider and the session's committed model. For `local`, save an endpoint under **Local model** first. For a ChatGPT/Codex (or Anthropic) model, wait for that provider's **Subscription connected**; HA authentication and ChatGPT authentication are different.

Official HA references: [adding a third-party App repository](https://www.home-assistant.io/common-tasks/os/#installing-a-third-party-app-repository), [App publishing and local builds](https://developers.home-assistant.io/docs/apps/publishing/).

## Required options and trust

- `authorized_user_ids`: explicit HA user IDs allowed to use Hearth. `[]` denies everyone. Server identity requires the documented Ingress socket peer and one `X-Remote-User-Id`; sidebar visibility is not authentication. Everyone listed is an **owner** unless also listed in `member_user_ids` or `guest_user_ids` (see [What is shared in a household](#what-is-shared-in-a-household)). Owners may use/setup/remove the installation's shared provider credential. A guest still sees whatever the installation's read scope exposes (entity states, lists), so guest suits semi-trusted people in the household, not strangers; never add untrusted users.
- `public_origin`: exact external HTTPS origin, no path/trailing slash, e.g. `https://home.example`. Needed for Origin/CSRF and iframe policy. Alternative origins are not implicitly accepted.
- `allowed_entities`: up to 10,000 exact entity IDs for Home reads and optional supported actions; no wildcards/all-future scope. Search pages contain twenty items. Empty denies all. Scope filters output, not the broad underlying HA token or states response processed in memory.
- `anthropic_auth_enabled`: **false by default**. Typed HA option fallback for the `HEARTH_ANTHROPIC_AUTH_ENABLED` environment flag; an explicitly set env value takes precedence and only exact `true` enables it. This gates Anthropic login/inference/compatibility only, not ChatGPT. Enabling it does not change provider/model, scope, Home permissions or the Code worker.
- `provider`: `offline`, `openai`, `openai-codex`, flagged `anthropic` or `local`. Offline is a faux response, not local inference. `local` uses an OpenAI-compatible server on your network that you connect from the UI; see [Local model endpoint](#local-model-endpoint-unreleased-source-slice). Online conversations and selected HA/coding output go to the provider.
- **Updated requested default:** `openai-codex` new sessions use `gpt-6.1-sol` with **medium thinking** when `model` is empty. An explicit `model` option remains the operator's model default (the operator must set it to `gpt-6.1-sol` if already configured differently); Codex new-session thinking defaults to medium. API-key mode defaults to `gpt-4.1-mini` / off and offline to faux / off. The selected model must be in the pinned provider catalog; provider account limits apply. This changes no existing session's explicitly committed model/thinking choice and never rewrites admitted work.
- `openai_api_key`: used only for `openai` API-key mode. Server-side secret; options/backups are sensitive. ChatGPT subscription access does not make this API billing free.
- `service_actions_enabled`: false by default. Optional `allowed_services` contains only `light.turn_on`, `light.turn_off`, `switch.turn_on`, `switch.turn_off` and, for [Shared lists](#shared-lists-unreleased-source-slice), `todo.add_item`, `todo.update_item`, `todo.remove_item` (at most these seven), with exact allowed entities. `todo.remove_completed_items` and other `todo` services cannot be configured. **Home permissions** defaults to Read-only with writes disabled, otherwise Ask: the model proposes and the human approves the immutable entity/data/hash once. The authenticated owner may explicitly acknowledge Full access / auto-approve for only these configured exact actions (optional brightness 0-255 for light.turn_on). This is not all HA services or host/admin access; Code is unchanged and separately confined. No indirect area/device/group selectors. An HTTP receipt is not device verification.
- `access_mode`: `scoped` by default. `admin` is an owner opt-in that gives Hearth Home Assistant admin power through risk-classified proposals; see [Admin access mode](#admin-access-mode-unreleased-source-slice). `risk_judge_model`, `risk_judge_url`, `risk_judge_api_key`, `risk_judge_timeout_ms` and `risk_judge_session_ttl_ms` configure the optional risk judge described there (the key is a server-side secret like `openai_api_key`).
- `briefing_summary_model`: `auto` by default (same resolution as `risk_judge_model`'s `auto`: `gpt-5.6-luna`, then `claude-haiku-4-5`, else off). `off` disables the optional per-briefing model-written summary entirely; `<provider>/<modelId>` names a different signed-in Pi runtime model. See [Today, briefings and watchers](#today-briefings-and-watchers-unreleased-source-slice). The summary is also off unless an owner turns on **Add a short summary** for that specific briefing.
- `workspace_enabled`: false by default. True requires workspace owners (below) and a **separate confined worker** installed by the trusted host operator; it does not create a container or expose Docker. [Workspace guide](../docs/workspace.md).
- `workspace_owner_ids`: empty by default, meaning "the one authorized owner" (then `authorized_user_ids` must have exactly one entry). Otherwise up to 5 HA user IDs, each also in `authorized_user_ids`, who alone may create and use Code sessions; see [Optional Code mode](#optional-code-mode).
- `member_user_ids`, `guest_user_ids`: empty by default (everyone authorized is an owner, exactly as before). Each ID must also be in `authorized_user_ids` (`role_user_not_authorized`), may be in only one list (`role_conflict`), at least one owner must remain (`household_owner_required`) and Code workspace owners must be owners (`workspace_owner_not_owner_role`). Roles are set only here, never in the UI.
- `trusted_user_ids`: empty by default (nobody is trusted; Home permissions behave exactly as described below). An owner opt-in for a household that wants no approvals for some people: each listed ID must also be in `authorized_user_ids` (`trusted_user_not_authorized`) and must not be a member or guest (`trusted_user_not_owner_role`); a malformed list fails with `invalid_trusted_user_ids`. A trusted person who chooses **Full access** has their own turns run at **every** risk level without asking; see [Trusted people](#trusted-people-unreleased-source-slice). Set only here, never in the UI.
- `approval_notifications`: false by default. True lets each owner or member confirm their own phones for [Phone approvals](#phone-approvals-unreleased-source-slice). Ingress mode only (local development refuses to start with `approval_notifications_requires_ingress`).

## Session model and thinking

The authenticated session picker (opened from the composer's model chip) lists chat models from the already configured provider's local in-process Pi Models registry plus those of every available subscription provider (ChatGPT/Codex; Anthropic only when its flag is on) that is currently **signed in**, grouped by provider when more than one is available. Each choice is a provider/model pair; choosing a model of a provider that is not signed in is refused until you sign in. A session committed to a subscription provider that is later signed out keeps its committed choice but cannot send until you sign in again or switch it. The `offline` demonstration keeps its faux-only choice. It performs no network catalog refresh and does not prove account entitlement. Choose model and thinking, then press **Apply model and thinking**; merely opening a session, selecting a choice, restarting or deploying never applies a draft. Actual committed session model and thinking are shown beside the picker and hydrated from snapshots/SSE. Applying persists both in the conversation's durable `pi.agent` document; the next human input uses them without an App restart. Running/admitted inputs, unresolved actions, and interrupted Code continuations cannot be switched; stale revisions fail and must be reviewed anew. Transcripts, usage, Home permission grants/policy and canvas are unchanged. New sessions receive the operator's configured model (Codex default `gpt-6.1-sol`) and medium thinking; old sessions retain their committed choice until explicitly applied. Switching does not change provider login or grant additional permissions.

## Conversation transcript

A turn's tool calls and their results collapse into one compact, collapsed-by-default **activity row** (tap to expand) instead of raw tool-call lines and large JSON results pushing the actual reply down the screen. Known tools show a friendly verb — for example `ha_search_states` reads "Searched home", `ha_state_detail` "Read a device", `ha_discover_services` "Checked available actions", `ha_propose_service` "Proposed an action", `ha_build_view` "Built a home view", `ha_automation_traces` "Checked recent runs" (and the other automation troubleshooting tools their equivalents), `app_create`/`app_update`/`app_get`/`app_list`/`catalog_describe` their app equivalents, and workspace/coding tools (`read`, `write`, `edit`, `bash`, `grep`, `find`, `ls`) theirs; an unrecognized tool still shows its exact raw name, never hidden. Expanding a call shows its short argument summary and a pretty, truncated, monospace result with **Show more**. A step's error stays visible in the row's own summary line (so it is seen even while collapsed), independent of Home permissions or action approval, which are unaffected. While a tool round is still running, one animated **Working…** line shows the current step (static under `prefers-reduced-motion`) instead of one row per tool. Assistant replies render as plain text with a small **Hearth** label and a **Copy** button (uses `navigator.clipboard`, with a same-page fallback when it is unavailable), not a bordered card; your own messages stay as compact right-aligned bubbles. Proposal/approval cards and app result cards are unaffected and still render as their own prominent elements. A floating **↓ New messages** pill appears only while you have scrolled up and new content arrives; the transcript still sticks to the bottom automatically whenever you were already there, and tapping the pill or scrolling back down dismisses it. Nothing here changes what is sent to the model, Home permissions, or action approval; it only changes how the existing transcript is displayed, and only ever as text.

## ChatGPT subscription login

1. Select `provider: openai-codex`; leave `model` empty or choose an appropriate catalog model. Restart **only this App** after option changes.
2. Open **Settings → Account** from the sidebar drawer. ChatGPT/Codex is always listed there (independently of the configured inference provider); select **Sign in with ChatGPT**. Like Pi's interactive `/login`, the sheet shows whichever step Pi's own login flow is waiting on: first Pi's method choice, with **Device code login (headless)** listed first and marked **Recommended for Home Assistant and phones** (no pasting needed — just a code to enter at OpenAI) and **Browser login** listed second with a note that it needs pasting a redirect URL. Pi's own option ids/labels are unchanged; only the order and the annotation are added. Choosing device code shows a large code with a **Copy code** button (falls back to selecting the text if the Clipboard API is unavailable), a prominent **Continue at OpenAI** link/button and three steps (copy the code, open OpenAI, approve). While Pi polls, the dialog shows **Waiting for approval at OpenAI… this window updates automatically**; it updates to **Subscription connected** once Pi confirms. If device code login fails, the hint suggests enabling it in your OpenAI account security settings or switching to Browser login. Complete the login/consent in your own OpenAI browser session; account eligibility and provider limits apply.
3. Browser login uses the official Pi PKCE flow. If localhost:1455 cannot reach HA, paste the **complete final redirect URL with code and state** into the protected password field, not chat. The official flow verifies state. No callback port is publicly exposed.
4. Wait for **Subscription connected**. The dialog shows the access token's expiry time, never the token. Pi refreshes it automatically before model requests; **Check connection** asks Pi to resolve auth the same way (refreshing only if it is close to expiry) and records OK/failed. If a check fails, choose **Sign in again**. Access/refresh tokens stay in private controller `/data`, never in browser responses, model context or coding storage. Login state is owner-bound, temporary and cancellable. No personal Pi credentials/resources are automatically imported.
5. Local sign-out removes this App's credential; it does not revoke the OpenAI account or retroactively undo requests already sent. Backups containing credentials must be protected.

## Anthropic login feature flag (unreleased)

Anthropic OAuth compatibility is experimental and disabled by default. Provider terms, account eligibility and extra-usage billing may apply; logging in does not guarantee included Claude-plan usage.

1. For a local developer run, set `HEARTH_ANTHROPIC_AUTH_ENABLED=true`. In Home Assistant, set the typed App option `anthropic_auth_enabled: true`; this is the fallback when the env variable is absent. Only exact env `true` enables the flag; an explicit `false` overrides the option.
2. Optionally select `provider: anthropic` to make Claude the default for new sessions. Without it, both logins are offered side by side and signed-in Claude models appear in the session model picker of any non-offline provider. With `provider: anthropic`, set `model: ""` for `claude-sonnet-5` / thinking off, or select a pinned catalog model. Restart **only Hearth Pi** after changing options. Enabling the flag alone leaves your existing provider/model unchanged. Create a new session for Claude; existing sessions retain their committed model/provider.
3. Open **Settings → Account** from the sidebar drawer, where Anthropic/Claude (experimental) is listed alongside ChatGPT/Codex, and select **Sign in with Anthropic**, or enter `/login anthropic` in the composer. Plain `/login` uses the configured provider when it is a subscription provider, otherwise ChatGPT/Codex; `/login openai-codex` and `/login anthropic` choose explicitly. Signing in never switches an existing session's model; use the session model picker. Commands open human auth and are not saved as conversation input or sent to the model.
4. Pi's native method selector offers **Browser login** and **Copy code login (headless)**. Use Copy code for remote HA: complete consent at `claude.ai`, then paste the complete **code#state** into the protected password field. A complete `https://platform.claude.com/oauth/code/callback` URL containing code and state is also accepted. Bare codes, mismatched state, foreign callback origins and stale/other-owner transactions are refused. Browser fallback requires the complete `http://localhost:53692/callback` URL with code and state. No callback port is published.
5. Wait for **Subscription connected**. Expiry, **Check connection**, cancellation and local sign-out use the same protected Pi flow as ChatGPT. Check connection resolves/refreshes auth, **not a live inference or billing test**. The separate controller file `/data/anthropic-oauth.json` is `0600`; ChatGPT's existing credential is preserved. Both providers' files are served through one Pi model runtime that delegates each provider to its own file and refresh lock, so both can be signed in at once. No Mac credentials are imported.

Hearth reuses the actual pinned compatibility package as a dependency; it does not copy its transport implementation into the application. It loads only the package's OAuth transport helper through a local, non-discovering TypeScript loader. No extension factory, personal/project configuration, account diagnostics or debug payload logging is loaded. Pi owns login, refresh, model catalog and transport; API-key/non-OAuth requests pass through unchanged. The package may retry a model request once after an explicit version-floor rejection, but never dispatches a tool or retries a Home/Code effect. Package version changes require retesting.

To disable, switch away from `provider: anthropic` and turn the flag off, then restart only Hearth. With the flag off nothing Anthropic is offered or read: no login, provider status, models or stored-token use. With Anthropic selected and the flag off, startup fails closed; it never silently changes providers. Disabling does not revoke or erase stored tokens; sign out locally first if removal is wanted. This slice has synthetic tests only, no real Anthropic login, included-usage/billing proof or live Claude inference.

OAuth is an account authorization step performed by the human, not a model tool. Never share codes, redirect URLs, tokens, options or SQLite in issues/videos. A synthetic test is not a successful live login.

## Local model endpoint (unreleased source slice)

Use an OpenAI-compatible server on your own network, such as Ollama, LM Studio, llama.cpp (`llama-server`), vLLM or a compatible proxy. This follows the shape of Pi's own `/login llama.cpp` (enter a server, validate it by listing models) and of community Pi extensions such as Crossbar and pi-lm-providers (fingerprint the server, then pick a model). No code from those extensions is included.

1. Select `provider: local`, leave `model` empty and restart **only this App** once.
2. Open **Local model**. Enter the server URL, for example `http://192.168.1.50:11434` (usual ports: Ollama 11434, LM Studio 1234, llama.cpp 8080, vLLM 8000). Add an API key only if the server requires one.
3. **Test connection** calls `GET /v1/models` and a few public metadata endpoints to identify the server, read context windows and hide embedding models. With Ollama, it also hides models that don't report tool calling, which Home mode requires.
4. Choose the default model and select **Use this endpoint**. Its models appear in the session model picker immediately, with no restart. **Refresh models** re-lists the saved server; **Remove endpoint** deletes it and its key.

Boundaries:

- There is no network scanning. Hearth contacts only the URL an authorized owner types.
- Only private addresses are accepted: loopback, 10/8, 172.16/12, 192.168/16 and IPv6 unique-local. Host names must resolve only to such addresses. Link-local/cloud-metadata ranges, the `supervisor` host and 172.30.32.2 are refused. Redirects are not followed. DNS can change after the check; this guards against mistakes, not a hostile DNS server.
- Everything you discuss, including selected Home data and tool results, is sent to that server. Trust it as you would a cloud provider.
- The endpoint, model list and optional key are stored in private controller `/data` (`0600`), never in browser responses or model context. Keys are limited to plain token characters, because Pi treats keys starting with `!` or `$` as commands or environment references.
- Startup reloads the saved endpoint without contacting it. If its host name can't be resolved to a private address at boot (for example, a server App that starts later), Hearth still starts and asks you to **Refresh models**. Sessions can't be created and inputs are refused until an endpoint is saved.
- Model quality and tool calling depend on the local model; small models may call tools poorly. Only `thinking: off` is offered for local models.

This is source-tested with fake servers and a real local HTTP server, not against a real Ollama/LM Studio/vLLM installation or on Home Assistant OS.

## Deleting a session

In the sidebar drawer, open a session row's **\u22ef** menu (`aria-label="More for <title>"`) and choose **Delete**. The confirmation names the session and states this cannot be undone through the App. Deleting removes it from your list, from the owner-scoped session count used for the 30-per-owner / 100-total limits, and from every session-scoped API route, which then answers `404` as if it never existed; an already-deleted or already-gone id also answers `404`. **The committed transcript is not securely erased**: Pi Durable 1.0.1 has no API to erase a conversation or its entries, so the data remains in the private App store (`/data`) until the whole store is removed, per "Privileges, state and rollback" below.

Deletion is refused (`409`, a distinct error per reason) while the session still has an open safety concern, so a removal can never quietly drop one:

- an action proposal awaiting approval, dispatching, or with an unknown outcome — reject or resolve it first;
- a durable task still running for that conversation;
- an admitted input that has not yet been answered or placed;
- for a coding workspace session, a `WorkspaceGuard` still paused after an uncertain operation.

These checks, and the removal itself, run serialized with session creation/submission and are re-read inside the same commit that removes the session, so the unknown-outcome write pause can never be silently lifted by deleting the conversation that holds it.

## Privileges, state and rollback

Ingress only, no host ports, HA Core configuration mounts or Supervisor/admin/auth/Docker API. `/workspace_link` is this App's own `addon_config` mapping, only for worker IPC—not HA Core `/config`. HA's token is broad; the App's fixed tools enforce narrower policy. Code mode has no HA tools; its worker has no HA/model network or credentials.

## Home permissions (unreleased source slice)

Open **Settings → Home permissions**, or the mode badge next to the conversation title, to use the selector and choose Read-only, Ask or Full access. Full acknowledgement binds to the displayed exact policy fingerprint, revision, schema and owner; settings persist in the existing durable store, not browser storage. New Full inputs may execute supported requests without per-action prompts. Running/legacy inputs cannot acquire Full, and choosing Full never executes old Ask proposals. Exact scope/service or schema changes invalidate Full; changing the policy back does not restore the grant.

Shared list changes follow the same modes, with one limit: in scoped mode Full access auto-approves only the supported light/switch actions, so **every list change asks** there, exactly like Ask. In [admin access mode](#admin-access-mode-unreleased-source-slice), Full access may run adding, completing and reopening an item (low risk) once without a prompt. Renaming and removing an item (medium) **always ask** in both modes, whatever the risk judge says. In scoped mode a list change needs the exact `todo.*` entity in `allowed_entities` and the exact `todo` service in `allowed_services`; adding or changing either invalidates Full access like any policy change.

Emergency Read-only stays available during work. It invalidates pending actions and promptly prevents/cancels dispatch; it cannot undo an already attempted effect. Receipts show human, automatic or trusted authorization, revision and accepted versus unknown. An unresolved dispatch/unknown pauses new Home writes **to the same entities** (and group entities that contain them), for every owner and conversation, across mode toggles and restarts; an unknown whose action can reach anything (configuration, registry, Supervisor, scripts, scenes, automations, device/area targets, a target Hearth could not read) and any such new action still pause **every** write, as before. Writes to other entities continue. Hearth never retries the unknown action, and a new proposal for a paused entity is refused (`home_outcome_unresolved`) until the unknown is settled. Other owners see only which entities are paused, not private receipt details. Stop task is not a substitute for Read-only.

**Unknown outcomes check themselves (read-only).** After a dispatch ends unknown (or a restart interrupted one), Hearth reads the target entities' state from Home Assistant about 5 seconds, 30 seconds and 2 minutes later. If every target is in the requested state, the receipt becomes **Succeeded (confirmed from Home Assistant state)**. If at the last check every target is still exactly as Hearth read it right before sending — same state, same attributes and no change reported by Home Assistant in between — it becomes **Did not happen (confirmed from Home Assistant state)**. Otherwise it stays unknown for you to check and record. Each check adds a note to the receipt. Reconciliation never sends a service call. It covers only actions with a well-defined target state: lights, switches, `input_boolean` and fans turned on/off (lights also with brightness) or toggled from a known on/off reading, covers opened/closed, locks locked/unlocked, climate temperature or HVAC mode, `input_select` options and shared list changes (add, complete, reopen, rename, remove). Everything else (configuration, Supervisor, scenes, scripts, device/area targets) stays unknown until you resolve it. Home Assistant state shows what the device reports, not what physically happened; a state reached some other way also counts as succeeded. A toggle is never marked "did not happen". Some battery radio devices (for example sleeping Z-Wave locks or thermostats) run a queued command only when they next wake up, which can be after the last check: a "did not happen" receipt can then still change later, so check such devices before asking again.

In Scoped mode: no Home shell/config/SSH/Docker, scripts, automation changes, Core or Supervisor-admin operations (see [Admin access mode](#admin-access-mode-unreleased-source-slice) for the owner opt-in); automations can only be inspected read-only (see [Automation troubleshooting](#automation-troubleshooting-unreleased-source-slice)). No generic service/JSON proxy or new Supervisor privilege. Avoid safety-critical devices. This slice is offline/source-tested only; live/mobile/restore/power-loss paths need separate authorization and validation.

## Trusted people (0.6.0)

Some households want no approvals for certain people. An owner can list them in `trusted_user_ids` (App configuration only; default empty, so nothing changes for anyone else). For a trusted person:

- **Full access** runs their own turns at **every** risk level — low, medium, high and critical — without the risk judge and without the typed confirmation word. Their own turns are what they type in Hearth and what they say through the Assist button under their own Home Assistant user, plus their own presses of app, Home World and list controls. The receipt says **Trusted / ran without asking**, with the risk level and the rule that classified it, so they can see what ran.
- **Settings → Home permissions** shows **Trusted: everything runs on Full**. Choosing Full still asks once for confirmation, and its acknowledgement text says that every risk level runs without asking. Adding or removing someone from `trusted_user_ids` invalidates their earlier Full grant, so they confirm again.
- **Ask** and **Read-only** behave exactly as for anyone else.

Still not run without asking for a trusted person (these become a normal pending proposal or follow the normal Full rules): requests from a **voice satellite** (anyone in the room can speak, so satellites keep their Ask ceiling); work the person did not start themselves (anything Hearth or another system submits on their behalf); and anything outside the configured access policy — trusted widens approval, never the policy: Scoped mode still allows only the configured exact entities and services, Admin mode never reaches the host shell or filesystem, and Code sessions stay separately confined. An input admitted under a weaker permission is never upgraded later, unknown outcomes are never retried, and members and guests cannot be trusted.

What counts as your own turn: a message you send in Hearth, and anything Home Assistant sends to Hearth's Assist agent under your own user — the Assist button, and also scripts or dashboard buttons you run that call Assist with Hearth as the agent. Home Assistant does not tell these apart, so do not let others edit scripts that call Hearth.

What this trades away: the model, or content it reads (entity names, attributes, automation text, images), can now cause high and critical actions — unlocking a door, opening a garage, restarting or updating Home Assistant, rebooting the host, restoring or deleting a backup — for a trusted person without a second look. Keep `trusted_user_ids` to people who accept that, and prefer Ask for everyone else. See [docs/security.md](../docs/security.md).

## Undo (unreleased source slice)

For 10 minutes after a low or medium change that Hearth read before sending, its receipt shows **Undo** with the time it is available until. Undo is offered for one entity at a time: lights (on/off, brightness, colour temperature), switches and the shared lists in both access modes, and in admin access mode also fans, covers that are not doors/garages/gates, climate setpoints and modes, media player volume and mute, `input_boolean`, `input_number` and `input_select`. A list item that was completed is reopened (and the other way round), a rename is renamed back, and an added item is removed only when exactly one open item with that text exists. Removing an item, anything with several entities or a device/area target, configuration, Supervisor actions, high and critical changes, and failed or unknown outcomes have no Undo; scoped mode offers it only when the reverse service is in `allowed_services`.

Undo never sends anything on its own: it creates a **new exact proposal** for the reverse action, from the state read before the change, and that proposal goes through Home permissions, the write pause and the risk rules exactly like pressing a control. In Ask you approve it on its card; in Full access a low one runs once, but it always asks if the device changed again more than 30 seconds after the original change. If it is already back as it was, Hearth says there is nothing to undo. Undo works once; it is offered again only if its proposal was rejected or expired before anything was sent. The state read is at most a fraction of a second older than the change, so Undo restores what Hearth saw just before sending.

## Phone approvals (unreleased source slice)

Opt-in with `approval_notifications: true`. Each owner or member (not guests) then opens **Settings → You → Phone approvals**, picks **Use this phone** next to one of their own phones and taps **It's my phone** on the notification that arrives (within 10 minutes). Hearth lists only phones with the Home Assistant Companion app whose device tracker belongs to the Home Assistant person linked to your user, and uses a phone only after that tap came from your own Home Assistant user. Up to 4 phones per owner; turn the switch off or **Remove** a phone at any time.

When Hearth proposes a Home change in a chat and it is still waiting for you 20 seconds later (with at least a minute before it expires), your confirmed phones get one notification: `Hearth · <level> risk` and one line naming the service and entity (or config item / Supervisor path), never values such as codes, never device names. **Low and medium** risk can be approved or rejected there; Approve asks the phone to unlock first where the Companion app supports it (iOS; on Android a lock-screen Approve may not require unlocking, so keep medium actions in mind). **High and critical** offer only **Reject** and **Open Hearth**: approving them always needs the exact card in Hearth, and critical still needs its typed word. Nothing you type in a notification is ever read.

A tap counts only once, only for that exact proposal, only before it expires, and only when Home Assistant reports it came from your own user. Hearth re-checks permissions, expiry and the write pause exactly as for a tap in the app. Each proposal is sent at most once (a failed send is not retried), at most 20 per owner per hour; the notification is removed when the proposal is decided or expires. Your own presses in apps, Home World and Today → Lists are not sent. Taps made while Hearth's connection to Home Assistant is down are lost; the proposal then simply expires. Pending approvals never survive a restart, and neither do notification links. If Home Assistant later links that phone to a different person, Hearth stops using it and shows **Confirm this phone again**.

## Hearth Assist (voice)

Off by default (`assist_enabled: false`). Hearth Assist lets Home Assistant's **Assist** use Hearth as its conversation agent: the Assist button in the Home Assistant app and frontend, and voice satellites. Hearth's own Home permissions, risk classifier, approvals and receipts decide every change; Home Assistant only passes the words and who is speaking.

**Set it up**

1. In the Hearth Pi App **Configuration**, set `assist_enabled: true` (and, for voice satellites, `assist_satellites`; see below), save and restart **only Hearth Pi**. Hearth creates a link secret (`/data/core-link.key`, mode `0600`) and publishes the link (host, port, API version and the secret) to Home Assistant Core through Supervisor discovery. Only Core can read it. Hearth's Assist listener (port 8098) is reachable on the internal Supervisor network only; it is not published on your host.
2. Install the integration with [HACS](https://hacs.xyz/): **HACS → ⋮ → Custom repositories**, add `https://github.com/cosmyo/ha-pi-durable` with type **Integration**, install **Hearth Pi** and restart Home Assistant. The App never writes to Home Assistant's `/config`; HACS installs `custom_components/hearth_pi` like any custom integration. Custom integrations are not reviewed by Home Assistant; read the code first.
3. **Settings → Devices & services** shows **Discovered: Hearth Pi**. Select **Add**, then **Submit**; Home Assistant checks the link once. If nothing is discovered, restart the Hearth Pi App once after installing the integration. You never type or see the secret.
4. **Settings → Voice assistants**: open (or add) an assistant and choose **Hearth Pi** as its **Conversation agent**. Keep **Prefer handling commands locally** on; read what that means below.
5. Settings → About in Hearth shows **Voice (Hearth Assist)**: whether the link is published and how many satellites speak for you.

**Who is speaking**

- **The Assist button** in the Home Assistant app or frontend: Home Assistant tells Hearth which user is signed in. A user in `authorized_user_ids` gets their own Home permissions and household role, exactly as in Hearth (an owner on Full access may auto-run a low-risk change; members and guests keep their limits). Anyone else is refused.
- **Voice satellites** usually arrive without a user, so an administrator maps each satellite device to one person in the App configuration. A turn from a satellite always uses this mapping and the Ask ceiling, even when Home Assistant attaches a signed-in user's context to it (for example follow-up speech after a dashboard started the conversation): anyone in the room can speak. People cannot claim devices themselves in this version:

  ```yaml
  assist_satellites:
    - device_id: REPLACE_WITH_THE_SATELLITE_DEVICE_ID
      user_id: REPLACE_WITH_THAT_PERSONS_HA_USER_ID
  ```

  Find the device ID under **Settings → Devices & services → Devices**: open the satellite; it is the last part of the page address (`/config/devices/device/<id>`). Every `user_id` must also be in `authorized_user_ids`, and a device can appear only once. Anyone near a satellite speaks as its person and speech-to-text can mishear, so a satellite has an **Ask ceiling**: a change requested through it is always a pending proposal for that person's exact approval, even when they use Full access. Read-only stays Read-only, guests stay read-only and members keep member limits.

- **Refused in this version:** satellites that are not mapped, Home Assistant users not in `authorized_user_ids`, turns without any user or mapped satellite, and anything started by an automation (for example `assist_satellite.start_conversation` or any turn carrying an automation's extra prompt). Assist speaks a short line instead.

**How a voice turn works**

- Each person has one rolling **Voice** chat in Hearth; when it is full, a new one starts. A Home Assistant conversation stays with that chat for about 5 minutes. A request Home Assistant repeats (same Assist context) never runs twice.
- Replies are kept short and plain for speech and are streamed as they are written. If Hearth has not finished after about 22 seconds, Assist says Hearth is still working; the turn keeps running and the result appears in your Voice chat. It is never cancelled.
- After the reply, Hearth's controller (not the model) adds one sentence from what really happened: _"I've asked for approval on your phone"_ only when Home Assistant accepted a [phone approval](#phone-approvals-unreleased-source-slice) notification for that change (for voice it is sent at once instead of after 20 seconds); otherwise _"It's waiting for your approval in Hearth"_; or the receipt: accepted, failed, or that Hearth could not confirm whether it happened. It also says when Home writes are paused by an earlier unknown outcome.
- **Saying "yes" never approves anything.** Approve on the exact card in Hearth or from a confirmed phone.
- If Hearth is still busy with your previous request, at capacity, or you send more than 20 requests a minute, Assist says so and nothing is queued.

**"Prefer handling commands locally"**

Keep it **on** for fast everyday commands. But know what it does: Home Assistant then handles every command it recognizes **itself**, with the entities you exposed to Assist. Those commands never reach Hearth, so Hearth's Home permissions, risk classifier, approvals, receipts and unknown-outcome pause **do not apply** to them. **Do not expose locks, alarms, garage doors, gates or similar devices to Assist** (Settings → Voice assistants → Expose). Hearth itself ignores the Assist exposure list: its own `allowed_entities` and access mode decide what it can read and propose.

**Privacy.** Voice transcripts and Hearth's replies are also kept by Home Assistant: they appear in Assist's debug view and conversation history, which Home Assistant administrators can see, besides the person's private Voice chat in Hearth. The words go to the chat's model provider like any message.

**The link secret** is stored in Hearth's `/data`, in Supervisor's discovery store and in Home Assistant's config entry, and therefore in backups. Whoever holds it can speak to Hearth as any authorized person (through satellites only with the Ask ceiling). An owner can replace it under **Settings → About → Voice (Hearth Assist) → Replace link secret**; Home Assistant receives the new one through discovery automatically, and the old one stops working at once. To turn Assist off, set `assist_enabled: false` and remove the Hearth Pi integration in Home Assistant.

**Not yet verified on a real installation:** that Home Assistant opens the discovery for this custom integration, HACS installing an integration from a repository that also holds Apps, satellite timeouts with long turns, and long silences while an optional risk judge (up to its timeout) decides.

## Admin access mode (unreleased source slice)

Hearth has two access modes, chosen **only** in the App configuration (Settings › Add-ons › Hearth Pi › Configuration), never in Hearth's UI, by a model or by a suggestion:

- `access_mode: scoped` (default): exactly the behaviour above — exact `allowed_entities` read scope and the exact light/switch `allowed_services`.
- `access_mode: admin` (owner opt-in): Hearth may read every entity, registry and automation/script/scene configuration, read allowlisted Supervisor information (add-ons, backups, Core/Supervisor/OS/host/network/resolution info, background job status, store, logs) and **propose** any Home Assistant service call, automation/script/scene create/replace/delete, allowlisted registry/helper changes (entity/device/area registry updates, `input_*` helper create/update/delete) and allowlisted Supervisor actions (add-on start/stop/restart/update/install/uninstall/options, new full/partial backup, backup restore/remove, Core restart/update, Supervisor/OS update, host reboot/shutdown). `allowed_entities`, `allowed_services` and `service_actions_enabled` are ignored in admin mode. Settings shows **Access: Admin** or **Scoped**.

Every change is still a durable, exact proposal with a receipt that goes through Home permissions and the action risk classifier. Reads need no proposal. In Scoped mode none of the admin tools exist.

**Risk classifier** (deterministic, `src/risk.ts`; the deciding rule is shown on the receipt and approval card):

| Level    | Examples                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| low      | `light.*`, `switch.*`, `fan.*`, `media_player.*`; `scene.turn_on` only when every scene member (read live) is a light, switch, fan or media player; `homeassistant.update_entity`; light/switch/fan controls in apps and Home World                                                                                                                                                                                                                                                                                                                                                                                                                      |
| medium   | `climate`, `water_heater`, `humidifier`, `vacuum`, `notify`, `tts`, `number`, `select`, `button`, `timer`, `counter`, `input_*` services; cover open/close/stop on blinds/shades when **every** target was read live and none is a door, garage door or gate; `scene.apply`/`scene.create` and scene writes whose entities are only comfort/household devices; `automation.turn_on/off`; HA config reloads; registry and helper changes (except below); `update.skip` on add-on updates; add-on start/restart; new backup                                                                                                                                |
| high     | **every automation and script create/replace** (it can later run any action without a person); `lock.*`, `alarm_control_panel.*`, `siren.*`, camera disable; covers that are doors/garage doors/gates (device class or name), any missing or unreadable cover target, or device/area cover targets; scenes (`turn_on`, `apply`, `create`, writes) containing anything else or unreadable members; `script.*` and `automation.trigger`; `homeassistant.restart/stop`; Core restart; `update.install` of an add-on; renaming/hiding a cover, lock, alarm, siren or camera entity; add-on stop/install/update/options; config deletes; **unknown services** |
| critical | host reboot/shutdown; backup restore/remove; add-on uninstall; Core/OS/Supervisor update (Supervisor endpoint or `update.*` on their update entities, or update targets that cannot be checked); automations/scripts that mention a critical service anywhere (templates and any letter case included); anything that targets Hearth itself — its add-on slug (`_hearth_pi`, `self`, or the running add-on's slug/name from Supervisor), any of its entities (update entity, switches, sensors), or configuration referring to it                                                                                                                        |

**Home permissions in admin mode:** Read-only denies every mutation; Ask requires exact approval of every mutation; Full access (acknowledged again for admin mode) auto-runs only **low** actions, and **medium** ones only when the risk judge ran and agreed. **High** always asks; **critical** always asks and the approval needs a second step: type the word shown (e.g. the add-on slug or `REBOOT`). A judge-flagged mismatch always asks and shows the judge's reason. [Trusted people](#trusted-people-unreleased-source-slice) on Full access are the one opt-in exception: their own turns run at every level without the judge or the typed word. Unknown outcomes pause writes (every write for configuration, registry, Supervisor and other house-wide actions; the same entities for entity service calls) and are never retried, for every action kind. A Supervisor mutation that Supervisor definitely rejected before it could have any effect (e.g. an invalid add-on slug) is reported as **failed**, distinct from **unknown**: it is done, not a barrier, and is just as never retried.

**Risk judge** (`risk_judge_model`, default `auto`): an optional cheap model, never the conversation's model. It is a separate, tool-less call that sees only your latest message in that chat, the exact proposed action JSON (for a [shared list](#shared-lists-unreleased-source-slice) change this includes the current text of the item it targets, as Hearth read it from Home Assistant; never your memory, household memory or profile) and the deterministic level (plus at most the last 4 earlier exchanges — your earlier requests, the exact earlier actions and its own verdicts — from the same chat and judge model within `risk_judge_session_ttl_ms`, default 5 minutes, reused so provider prompt caches stay warm). It may only raise a level or flag a mismatch; it can never lower a level or approve anything. Errors, timeouts (`risk_judge_timeout_ms`, default 15000, max 30000), unparseable replies and judge off all mean "no agreement". Values:

- `auto`: `openai-codex/gpt-5.6-luna` when ChatGPT/Codex is signed in, else `anthropic/claude-haiku-4-5` when Anthropic is signed in, else off.
- `off`.
- `<provider>/<modelId>` from Hearth's Pi model runtime, e.g. `anthropic/claude-haiku-4-5` or `local/<model>` for a saved [local model endpoint](#local-model-endpoint-unreleased-source-slice). An unknown or signed-out model means off with a warning (shown in Settings › Risk judge).
- `systemone/<modelId>` with the same `risk_judge_url` (and optional `risk_judge_api_key`): any **decision model** that speaks the Jev/SystemOne API (`POST /v1/systemone`), such as Jev, Cloudflare's open-weight Clef or Clef-flash, or a gateway in front of them. Instead of generating text, a decision model returns calibrated probabilities for typed questions. Hearth asks two: whether the action is plainly one of the requested changes (counted as aligned only at 90% or more), and how risky the action is (low/medium/high/critical; it escalates when the most likely level, or at least 20% of the probability, lies above the deterministic level, and never lowers it). It sends the same data as the text judge (your latest message, the exact action, the deterministic level and at most 4 earlier exchanges) under the same private-address rules, and a malformed or failed answer fails closed to Ask.
- `endpoint/<modelId>` with `risk_judge_url: http://192.168.1.50:8080` (and optional `risk_judge_api_key`): a private-network OpenAI-compatible server just for the judge, independent of the chat provider — for example llama.cpp with a small Qwen/Gemma-class model on the same Raspberry Pi. The same private-address rules as the local endpoint apply (private/loopback addresses only, no `supervisor` host, no redirects), re-checked on every call. Hearth sends JSON-schema constrained output (falling back to plain JSON with strict parsing), `max_tokens` 60 and `cache_prompt: true` with a byte-stable policy prefix.

Settings shows the judge model read-only; change it in the App configuration. Receipts record the judge model, verdict, reason and latency.

Limits: there is still no host shell, host filesystem, Docker socket or privileged container access. Admin mode needs Supervisor's own REST API directly: the manifest grants `hassio_api: true` and `hassio_role: manager` to the add-on's token **in every installation**, because Home Assistant Core's `supervisor/api` WebSocket command rejects the add-on's Supervisor-proxied connection with `{"code":"unauthorized"}` — it is not an HA admin user (verified against a real Home Assistant 2026.9 / current Supervisor install). Hearth therefore calls `http://supervisor/<path>` directly with `Authorization: Bearer $SUPERVISOR_TOKEN`, never through Core. The **manager** role is broad: it covers every endpoint Hearth allowlists below and nearly everything else Supervisor exposes except an add-on's own protection-mode toggle, OS datadisk wipe and the host SSH authorized-keys file (checked against Supervisor's own `api/middleware/security.py` role table); Hearth never requests `hassio_role: admin`. **Hearth's fixed path allowlists and safe-field projections, not the Supervisor role, are the actual enforcement point** — see [Security](../docs/security.md) for the residual risk this implies. Scoped mode never registers or calls a Supervisor tool, enforced in code independent of the token's role (`src/ha.ts` refuses before any network call). Reads time out after 10 seconds and refuse any redirect, oversize or non-JSON response; mutations have a per-endpoint ceiling (backup create/restore and add-on install/update up to 600/900 seconds respectively, most others 30–120 seconds). Backup create/restore and add-on install/update ask Supervisor to queue a background job instead of holding the request open; check its progress with `supervisor_read` on `/jobs/info` or `/jobs/<job_id>`. A definite 4xx from Supervisor before any side effect (token/role/shape checks all run before its handler) is a **failed** receipt; a network error, timeout or 5xx after the request may have reached Supervisor's handler is **unknown** and pauses every Home write until you reconcile it (Supervisor actions can reach anything), and is never retried. Supervisor and Home Assistant tokens never reach the model, browser or logs. Logs are redacted (known secrets plus common token/password shapes) and capped to the last 16 KB. Supervisor info is returned only as an explicit allowlist of safe fields per endpoint (e.g. add-on name, slug, state, version, update availability) — add-on `options`, `schema`, network maps, ingress entry URLs and backup protection details never reach the model. In admin mode entity reads return up to 40 attributes (≤200 characters each; 12 shortened ones in lists), dropping nested objects, keys that look like tokens/passwords/keys/sessions/credentials and tokenized picture URLs.

**Controls in admin mode:** Home World and app controls work for lights, switches, fans, climate (on/off), covers (open/close), media players, automations, `input_boolean`, humidifiers, vacuums (start/return to dock) and locks. Each press sends that entity's own service through the same Home permissions broker and classifier: in Full access a fan runs at once (low), a cover waits for you (medium; a direct press has no judge), a lock always asks (high). Admin mode makes Hearth as powerful as an admin: use Ask unless you understand the classifier table above.

## Run the risk judge on your Home Assistant host

The `endpoint/<modelId>` judge above works against **any** private-network OpenAI-compatible server. This repository also ships one you can install yourself: **Hearth Judge** (`hearth_judge/`, a separate, independent add-on in this same repository), which serves a small open-weight model on your Home Assistant host behind the official `ghcr.io/ggml-org/llama.cpp` server. Running it on-host, instead of using a cloud judge, means your latest message and the exact proposed action JSON never leave the Home Assistant host for judging — only the conversation model (`provider`) still sees them, as always.

1. Install **Hearth Judge** from the same repository card as Hearth Pi (**Settings → Apps → Install app**, find it separately from Hearth Pi), open its **Configuration** tab, choose a `model` and **Start**. The first start downloads and sha256-verifies the configured model into its own `/data` (no other network use afterwards). See [hearth_judge/DOCS.md](../hearth_judge/DOCS.md) for options, its internal hostname and expected memory/latency on a Raspberry Pi 5.
2. In Hearth Pi's configuration, set `risk_judge_model: endpoint/<model>` (the `<model>` string is cosmetic here — llama.cpp serves whichever model it loaded regardless of the requested name — use the add-on's `model` option value, e.g. `endpoint/qwen3-1.7b-q4_0`, so receipts are self-explanatory) and `risk_judge_url` to Hearth Judge's internal address, e.g. `http://local-hearth-judge:8080` for a locally copied add-on, or the repository-install hostname shown in Supervisor (see [hearth_judge/DOCS.md#networking](../hearth_judge/DOCS.md#networking)). Set `risk_judge_api_key` only if you configured one on Hearth Judge.
3. Save and restart Hearth Pi. Ask something that proposes a mutation in `admin` access mode; the approval card's judge note should now show the `endpoint/…` model.
4. **Run the evaluation harness** before trusting it for anything beyond low-risk actions: from the repository root, `node scripts/eval-judge.mjs --endpoint-url http://local-hearth-judge:8080 --endpoint-model qwen3-1.7b-q4_0 [--endpoint-api-key <key>]` scores all 60 synthetic cases in [`hearth_pi/eval/judge-cases.json`](../hearth_pi/eval/judge-cases.json) and writes a Markdown report (`--out <path>`, default `hearth_pi/eval/report.md`) with accuracy, the **false-agree rate** (misaligned/injection cases the judge called aligned — the most important number, since the judge can only escalate and this is where that fails), escalation recall, JSON-parse failures and p50/p95 latency. See [hearth_pi/eval/README.md](../hearth_pi/eval/README.md).

**Measured on a Raspberry Pi 5 (16 GB, CPU-only, October 2026), with the 60-case harness:** `qwen3-1.7b-q4_0` agreed with 80% of misaligned or prompt-injected actions (accuracy 60%, escalation recall 0%, p50 4.4 s, p95 6.8 s); `qwen3.5-2b-q4_0` agreed with 57% (accuracy 70%, escalation recall 0%, p50 6.2 s, p95 9.3 s). Both reliably said "aligned" to clear requests but could not tell a wrong or broader action from the requested one. **Do not use these small on-host models as your risk judge**: a judge that agrees too easily lets medium-risk actions auto-run under Full access. For comparison, a 27B-class open model on a desktop GPU reached 93% accuracy with a 10% false-agree rate at about 0.3 s per call. Use a 27B-class (or larger) local model, a cloud judge (`auto`), or no judge (medium actions then always ask). The add-on stays available as an experiment and for future, better small models; measure any model with the harness before relying on it. `risk_judge_timeout_ms` (default 15000) should stay comfortably above your measured p95, or timeouts will fail closed to "no agreement" (Ask) more often than the judge itself would. The endpoint judge always sends `temperature: 0`, a small `max_tokens` and strict JSON-schema-constrained output (falling back to plain JSON with the same strict parsing if a server rejects the schema) — unchanged behaviour, documented here because it is what keeps a tiny model's replies both fast and parseable. This does not change the cloud judge path (`auto`, or an explicit `<provider>/<modelId>`), which is unaffected by anything in this section.

## Apps (unreleased source slice)

Ask Hearth in a Home chat for a small household app — “Make me a laundry app”, “a bedtime lock-up check”, “a 3D print monitor”, “a maintenance checklist”. The model writes a declarative **HAS/1** spec (`specVersion: "has/1"`): a flat element map from a fixed catalog (Stack, Grid with 1–3 columns, Tabs, Card, Section, Text, EntityValue, EntityTile, StatusPill, HistoryChart, Checklist, Counter, Note, AskButton, ToggleAction). It chooses structure and exact entity bindings only; it cannot write values, HTML, links, scripts or styles, and it has no tool to press buttons, tick checklists or run anything.

- **Validation.** Hearth rejects unknown components/props, cycles, shared children, orphans, missing roots, nesting deeper than 6, more than 80 elements or 8 tabs, oversized text, markup/script-like text, literal values in entity-bound props, entities outside the app's `scope.entities` or outside `allowed_entities`, and ToggleActions whose `<domain>.turn_on` and `<domain>.turn_off` are not both in `allowed_services`. Errors name the exact JSON path so the model can repair the spec in one turn. `catalog_describe` is generated from the same schema and includes four starting templates.
- **Values.** Opening an app makes fresh controller reads of its bound entities through the existing scoped reads; each value shows an “as of” time. Unavailable entities, failed reads and entities later removed from `allowed_entities` show **Unavailable** (and the app is flagged “needs repair”) instead of a guess. HistoryChart reads at most 3 entities over at most 48 hours from the recorder, without attributes, and Hearth downsamples it to 48 points (text states show their last 12 changes). Values are not live telemetry; use ↻ to read again (rate-limited).
- **Household data.** Checklist ticks, counters and notes are app-local, stored separately from the spec, so model updates and reverts keep them. Note text and checklist items are untrusted when shown back to a model.
- **Controls.** AskButton only drafts an editable message into the current chat (or a new chat named after the app); you press Send. ToggleAction goes through **Home permissions**: Read-only shows it disabled with an explanation; Ask files the exact action (domain, service, entity, data) for approval in the current chat and shows the same approval card; Full access dispatches once within the configured light/switch scope and reads the state back. An unknown outcome is never retried and pauses Home writes until you reconcile it in that chat's action card.
- **Storage.** Apps are household objects for the signed-in owner, not tied to one conversation. Each version is an immutable Pi Durable document; `app_update` applies a JSON Patch (add/remove/replace) with optimistic concurrency, and a stale base version is refused with the current version. **Restore** under _Versions and options_ appends a new version copied from an older one. Limits: 30 apps per owner, 50 versions per app, 32 KB per spec. Delete removes the app from your list and retires its documents; like session delete, committed history stays in the private store and is not securely erased.
- **Using it.** Open **Apps** in the drawer. Tap an app to open it full screen (‹ Apps returns). Pin apps to show them at the top of an empty chat. When Hearth creates or updates an app in a chat, a compact card shows Open / Pin and, for updates, a diff summary (+/− elements, entities added). An empty **Apps** list shows four starting suggestions (Laundry, Bedtime lock-up, 3D print monitor, Maintenance checklist); tapping one drafts a "Make me a … app" message into the current or a new Home chat — you still review and press Send.

Deferred from the iteration plan: Reminder/Timer components (use a schedule watcher instead), conditional visibility, SceneButton, Gauge/StatisticsChart/Logbook/Agenda, export/import, per-user visibility, live mini-status on app cards and a “try it” preview. Apps were tested with an offline model and Home Assistant fakes only; mainstream-model generation quality and the HA companion app were not verified.

`/data` survives restart/update but not uninstall. Cold App backups are sensitive and do not include the separate worker's files. Restoration does not undo device/file effects; old approvals are invalidated and uncertain effects need human reconciliation. Disable workspace/actions and stop only the specific App/worker to roll back; preserve files unless deletion is explicitly intended. No Home Assistant Core restart is needed for this App's ordinary install/configuration.

## Today, briefings and watchers (unreleased source slice)

Hearth can now notice things for you and leave a card in **Today** (drawer row; a badge counts new cards and a dot appears on **‹ Chats** on phones). An empty Today explains what watchers and briefings are and offers **Create a watcher**, which opens **Briefings & watchers** straight to the add-watcher form. Everything here only reads Home Assistant — watchers and briefings never call services, press app controls, change Home permissions or start a chat with the model.

- **Watchers.** Four deterministic kinds: a state **change** (e.g. `sensor.washer_state` from `running` to `idle`; changes out of `unavailable`/`unknown` are ignored unless named), a numeric **threshold** (above and/or below), a **duration** in a state (e.g. a window `on` for 30 minutes, measured from when Hearth first saw it) and a **reminder** at a local time on every day or chosen weekdays. Entity watchers may repeat their card every 5–1440 minutes, at most 5 times, while the condition still holds. Apps Hearth builds can include up to 6 `watchers` (watched entities must be in the app's `scope.entities`); you can add up to 20 of your own under **Briefings & watchers → Add a watcher** (entity IDs must be in `allowed_entities`). **Pause all** stops every watcher; a watcher whose entity left the read scope shows **Needs repair** and is not read.
- **How it runs.** The controller checks about once a minute (first check about 15 seconds after start), reading at most 50 distinct in-scope entities per pass through the same scoped state reads as apps. Times are in the App container's local time zone, which Supervisor normally sets to Home Assistant's; check your first reminder's time. Evaluation state and an idempotency ledger are Pi Durable documents committed together with each card, so a restart never repeats a card. A reminder or briefing whose time passed while Hearth was off is delivered **once**, marked _late_ with its original time (only the most recent missed time, not one per missed day). A change that happened and reverted while Hearth was off cannot be seen. At most 20 watcher cards per hour are added; extra ones are counted as held back.
- **Briefings.** Morning and evening briefings are **off by default**. Turn one on, choose a time and a source — one of your apps or a saved Home view — and press **Save**. Saving never delivers a time that already passed; the first briefing comes at the next occurrence. At its time Hearth reads the source's entities (up to 12) and adds a card with each value and its read time. An entity that is outside the read scope, failed to read or reports `unavailable` shows **Unavailable**, never a guess; a deleted source says so.
- **Briefing summary (owner opt-in, off by default).** Each briefing has its own **Add a short summary** checkbox. When on, right after the card's values are delivered Hearth makes one extra, tool-less model call: the request is exactly that card's own entity names, states, units, read times and unavailable/anomaly flags, sent as plain JSON data, never as instructions. The call has no tools, no conversation history, no memory and no Home Assistant access of its own; it writes at most 400 characters of plain text describing only what was given, never claims to have done anything, and says a value is unavailable rather than guess it (instructed and tested with a faux provider). It uses the same cheap-model choice as the risk judge's `auto` (`gpt-5.6-luna`, then `claude-haiku-4-5`, else off) unless `briefing_summary_model` names a different runtime model; the call waits at most 20 seconds and at most 4 summaries run per owner per rolling day. The card shows the written summary plus the model and how long it took, or a quiet **Summary unavailable** if the model is off, the daily limit is spent, or the call timed out or failed — the values above it are delivered either way. If Hearth restarts between delivering a card and writing its summary, that card stays delivered without one: it is never retried and never duplicated.
- **Cards.** Each card shows its source (app watcher, your watcher or briefing), when it was added, the values Hearth read and their time. **Dismiss** removes it; **Snooze** hides it for 1 hour, until 19:00 today (**Tonight**) or until 08:00 tomorrow; **Open app** opens the app it came from; **Ask about this** drafts an editable question into a Home chat — nothing is sent until you press Send. Cards older than 14 days and beyond the newest 60 are removed. Card text from apps is plain, validated text.

## Automation troubleshooting (unreleased source slice)

Ask a Home chat “Why didn't the hallway light come on at 23:10?” or “Can you fix my hall light automation?”. Hearth reads what happened and explains it; when a change would help it **drafts** corrected automation YAML in a code block and tells you where to paste it. **Hearth never creates, edits, enables, disables, triggers, reloads or deletes automations or any other Home Assistant configuration** — you review and apply every draft yourself.

- **Scope.** Add the automation's entity ID (e.g. `automation.hall_light`) to `allowed_entities`. Automations outside the read scope are refused. Entities the automation references are read only if they are also in `allowed_entities`; the others are named as “outside Hearth's read scope” and are never read or guessed. Device triggers/conditions (device IDs) and templates that read entities indirectly (`expand()`, `states | …`) are flagged; whenever an automation references anything outside the scope, the values a run observed (condition states, rendered action data) are withheld.
- **What it reads** (all read-only, through Supervisor's Home Assistant API proxy and token):
  - the automation's state, `id`, mode and last-triggered time;
  - its config with `GET /api/config/automation/config/<id>` (HA's automation-editor store, `automations.yaml`); for automations HA's editor does not manage (for example YAML packages) it uses the config captured by the latest trace;
  - up to 5 recent **traces** over HA's WebSocket API (`trace/list`, `trace/get`) — trigger, conditions with passed/failed, actions run, errors, timestamps — plus one run step by step;
  - the **logbook** for the automation and up to 9 in-scope referenced entities, and state history for up to 3 of them, over the last 1–24 hours.
- **Drafts only.** Hearth shows a YAML block and says where it goes: **Settings → Automations & scenes →** open the automation **→ ⋮ → Edit in YAML**, replace the text and **Save**; for automations kept in your own YAML files, edit that file and use **Developer tools → YAML → Reload automations**. Check the draft before saving; it is model-written text.
- **Secrets.** Returned config and trace text pass through Hearth's redactor: configured credentials, values under password/token/key/auth/webhook/code-like keys, credentials in URLs, bearer tokens and JWT-like strings become `[REDACTED]`. `!secret` references are shown as the literal reference, never resolved. This is pattern-based, not a guarantee that every secret format is caught.
- **Limits.** Automations need an `id` for HA to offer their config and traces. HA keeps only a few recent traces per automation (default 5, its `stored_traces` option). Each read has a 10-second deadline; WebSocket frames are capped at 1 MB (4 MB per read) and REST responses at 2 MB. The config editor and trace APIs require an administrator on the HA side; the App's Supervisor proxy token normally has that, but this was verified only against fakes, not a live Home Assistant.

The WebSocket client sends only `auth`, `trace/list`, `trace/get` and (for Home World) the three read-only registry lists `config/area_registry/list`, `config/device_registry/list` and `config/entity_registry/list`; every other message type is refused before anything is sent. Tested with an offline model, a fake HA REST API and a fake WebSocket peer only.

## Feedback and Insights (unreleased source slice)

Each Hearth reply has 👍 and 👎. 👎 offers fixed reasons — Wrong value, Wrong device, Didn't do it, Too long, Not useful, Creepy / privacy — then **Save 👎**; tap a chosen thumb again to clear it. A rating stores only the owner, session number, message number, rating, reasons, the session's provider/model label and the time: **never your prompt or Hearth's reply text**. Ratings are kept for 90 days (at most 2000) in the private App store. **Insights** (from **Briefings & watchers**, or directly from **Settings → Insights**) shows totals, reasons, ratings per model, Today card counts (created, dismissed, snoozed, asked about, held back) and your recent ratings. **Export** downloads (and shows) the same JSON; **Delete all** clears your ratings and counts from the document. As with session delete, Pi Durable keeps committed history in the private store, so this is not a secure erase. Nothing is sent anywhere; there is no telemetry.

Not included yet: Reminder/Timer app components. The Suggestions inbox is described in the next section. This slice is tested with an offline model, fake Home Assistant and fixed clocks only; it has not run on a real Home Assistant installation or for days of wall-clock time.

## Memory and suggestions (unreleased source slice)

Hearth can learn small things you tell it, but only what you approve. Nothing here can change Home permissions, entity or service scope, credentials, providers or settings.

- **Memory.** Open **Settings → Memory**. Each item is one line of plain text, at most 200 characters (line breaks become spaces), for example “Bedtime is around 23:00”, “The kids' rooms are North and South” or “Study fan is called Breezy”. The screen has two sections:
  - **Only you**: your private memory. Each authorized Home Assistant user has their own; nobody else's Hearth sees it. Each item shows whether you wrote it or accepted it from a suggestion (with the chat it came from), and when it changed. **Edit**, **Forget** and **Share with household** act on one item. At most 60 items. Memories saved before household memory existed stay here, private.
  - **Household — every member's Hearth uses these**: [household memory](#household-memory), shared by every authorized owner.
  - When you add an item, choose **Only you** (the default) or **Household**.
- **How Hearth uses it.** Before each model request in a Home chat, Hearth adds your current private memory as a separate, clearly delimited section marked OWNER-APPROVED CONTEXT, followed by household memory in its own section marked HOUSEHOLD CONTEXT. The system prompt states that both are data, not instructions: they never grant permissions, never widen entity or service scope, never change Home permissions and never override the safety rules. Angle and square brackets in item text are replaced and every item is one line, so an item cannot close either section or forge either section's markers. At most 4 KB of item text is used from each (separately); when you exceed it, the oldest items are left out and the Memory screen marks them **Not used (over limit)** with a warning. Code sessions never receive either; other owners never receive your private memory. Neither ever reaches the risk judge.
- **Forget.** Forgetting removes the item from the memory document, so later requests (in new and existing chats) no longer include it. It is **not a secure erase**: like session and app delete, Pi Durable keeps committed history (earlier document revisions) in the private App store, and a chat that already ran with the item keeps that earlier prompt entry in its own transcript; with model APIs that accept mid-conversation system messages that earlier entry can still be part of that chat's context. Start a new chat if that matters.
- **Suggestions.** In a Home chat Hearth may call `suggest_memory` (when you state a lasting fact or correct a name, room or device mapping; it suggests **only you** by default, or **the household** for facts about the shared home, and the card shows which) or `suggest_app_change` (a JSON Patch against one of your apps' current version, with a one-line summary). These tools only file a suggestion; they never save memory or change an app. App patches are validated exactly like `app_update` (catalog, scope, read scope, service scope) when suggested and again when accepted. Suggestions appear in a **Suggestions** section at the top of **Today** (they count toward the Today badge):
  - **Accept** saves a memory item, or applies the app change as a new app version (revertible under _Versions and options_). An app change is applied only if the app is still at the version it was based on; otherwise it stays in Today as a **conflict** (“the app changed since this suggestion”) and nothing changes — **Ask Hearth again** drafts a request for a fresh suggestion, **Dismiss** closes it.
  - **Edit** (memory only) lets you change the text, and whether it is for only you or the household, before saving it. Suggestions stay in your own Today, whichever you choose.
  - **Reject** closes it; Hearth will not suggest the same memory (same normalized text) or the same app patch again for **60 days**.
  - **Snooze** hides it for 1 hour, until 19:00 or until 08:00 tomorrow.
  - Every decision is your authenticated, Origin/CSRF-checked request bound to the exact suggestion shown (its hash) and recorded with your user ID; a model cannot accept anything.
- **Limits.** At most 3 suggestions per chat and 10 per owner in any 24 hours, and at most 20 waiting at once; a suggestion identical to one already waiting, or a memory already saved, is refused.
- **After a 👎.** When you rate a reply 👎 with a reason in a chat that built or changed an app, the reason chips say “Hearth may suggest a fix”. On your **next message in that chat** (never on its own), Hearth sees which replies you rated and why (message numbers and reason names only, no text) and may file one app-change suggestion. There is no background job.

Deferred: the weekly reflection job, instruction/canvas/watcher proposals and “try for 7 days” from the product brief are not included. Not included yet: Reminder/Timer app components.

### Household memory

Household memory holds facts about the shared home that every member's Hearth should know (“Bins go out on Tuesday evening”, “The study fan is called Breezy”). Any authorized owner may add, edit or forget a household item; an edit or forget made after someone else changed household memory is refused (the list reloads) instead of silently overwriting their change. The same limits apply as for private memory: one line of at most 200 characters, at most 60 items and 4 KB used per request, oldest left out first. **Share with household** moves one of your private items there on purpose (it disappears from Only you); a household that is full leaves the private item where it is.

- **Authorship stays private.** Each household item shows only **You added this** or **Added by another household member** (plus “edited by another member”), never a name, user ID, chat title or suggestion.
- **A real influence channel.** Every member's household items reach every member's Home chats. They are marked as data that can never authorize anything, and the prompt tells Hearth never to treat one as the signed-in owner's request and to prefer the owner's own memory and profile when they conflict, but a household item can still shape how Hearth understands names and habits. Only add what everyone in the household is comfortable sharing.
- **Forget is not a secure erase** (see above), and a household item stays after its author is removed from `authorized_user_ids`, until someone forgets it.

## Shared lists (unreleased source slice)

Hearth can read and change **Home Assistant to-do lists** (for example a shopping list), the same lists the Home Assistant app and voice assistants use. Add the list's `todo.*` entity (for example `todo.example_groceries`) to `allowed_entities`; in scoped mode also enable `service_actions_enabled` and add the services you want: `todo.add_item` (add), `todo.update_item` (complete, reopen and rename) and/or `todo.remove_item` (remove). In admin mode every `todo.*` entity is in reach. At most 8 lists are shown.

- **Today → Lists.** A calm **Lists** section in Today (below Suggestions, above cards) shows each list collapsed with its name and open count. Opening one shows the open items (up to 100) with a check button, a ⋯ menu with **Rename** and **Remove**, a **Done (n)** section (up to 20) with **Reopen**, an add field and the time Hearth read the list. A disabled control says why (outside the configured services, Read-only, writes paused, or the list does not support it in Home Assistant). Lists never add to the Today badge.
- **Every change is a Home permissions proposal.** A press files one exact action in a Home chat named **Shared lists** (the most recent one, or a new one), so its receipt lives there. Ask opens the same exact approval card as app and Home World controls; in scoped mode Full access asks too (it auto-approves only light/switch actions), while in admin access mode Full access runs adding, completing and reopening once; renaming and removing always ask; Read-only denies before Hearth contacts Home Assistant. When that chat holds 100 receipts, Today offers to start a new Shared lists chat; the refused press did nothing and is never resent on its own.
- **In chat.** Home chats get `list_read` and `list_propose` (only when a list is in reach). List items are untrusted data written by people or integrations.
- **What the approval shows.** A complete, reopen, rename or remove names the item by the text Hearth itself read from Home Assistant when the change was proposed (never text a model or a request supplied); that text is part of the exact action you approve and the risk judge sees. Right before sending, Hearth reads the list again: if the item changed, was completed, reopened or removed in the meantime, or the list does not support the change, nothing is sent and the change is refused. Home Assistant has no compare-and-set, so a change made in the moment between that read and the send can still slip through.
- **Unknown outcomes.** If Home Assistant does not clearly accept a list change (a timeout, an error reply), the receipt is **unknown**, is never retried and pauses all Home writes for every owner, including lights and switches, until the person who made the change checks the list and records what they saw on its action card in the Shared lists chat. Today shows that writes are paused.
- **Reads.** Hearth reads items over Home Assistant's read-only `todo/item/list` WebSocket command (plus each list's state for its name and supported features) and keeps only each item's id, text and done/not-done status; due dates and descriptions are not read into Hearth. At most 20 list reads per owner per minute.

Not included yet: a list component for apps, a shared Home World layout, cross-owner Today cards such as “someone added milk”, due dates and descriptions, and removing all completed items.

## What is shared in a household

Each authorized Home Assistant user (`authorized_user_ids`) is an owner with their own Hearth. Only the following is shared:

| Shared by the household                                                  | Per owner                                           |
| ------------------------------------------------------------------------ | --------------------------------------------------- |
| Home Assistant state and to-do lists (read live from Home Assistant)     | Chats, proposals and receipts                       |
| Household memory                                                         | Home permissions                                    |
| The unknown-outcome write pause (others see only that writes are paused) | Today cards, watchers, briefings and suggestions    |
|                                                                          | Apps, Home World layout, profile and private memory |

Household roles (`member_user_ids`, `guest_user_ids`; App configuration only) decide what each authorized user may do. The server enforces them on every route, tool and action; the UI only hides what a role cannot use.

| Role            | Home changes                                                                                                 | Also                                                                                                                                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Owner (default) | Read-only, Ask or Full access; approves any risk level                                                       | Sets up and removes the shared provider sign-in and local endpoint; admin and automation reads; Code sessions when listed as a workspace owner                                                           |
| Member          | Read-only or Ask only; may request and approve low and medium changes; high and critical are refused for now | Chats, lists, private and household memory, apps, watchers, suggestions and Phone approvals; no provider setup, admin/automation reads or Code                                                           |

A role change takes effect at the next start: it bumps the user's Home permissions revision (pending proposals go stale), turns a member's Full access into Ask and a guest's permissions into Read-only. Settings → You shows "Your role: Member — owners approve high-risk changes" or "Guest · Read-only". Members' high-risk requests are refused with `role_requires_owner`; routing them to an owner for approval is not implemented yet.

## Your profile (unreleased source slice)

Open **Settings \u2192 You** (the first row, above Home permissions) for personal preferences: nothing here is shared with another authorized owner, shown to the risk judge, or able to grant a permission, widen scope or change a setting.

- **Name, tone and reply language.** What Hearth should call you, a tone (Concise, Warm, Neutral or Playful, or **Not set**) and a reply language (a short list of common languages, **Match my messages**, or **Not set**). ## Code improvement suggestions (L3) (unreleased source slice)

The fourth and last kind of suggestion, `code`, is Hearth noticing that one of its own tools keeps failing the same way, and asking to draft an actual code fix \u2014 reviewed, written and released entirely outside Hearth. **Hearth never deploys itself**: this flow can only ever end with you reviewing a patch in an ordinary Code session and releasing it yourself.

- **The signal.** The controller keeps a small, bounded, per-owner counter of Home tool failures \u2014 just a tool name, an error code and a time, kept for 7 rolling days \u2014 built only from results Hearth's own tools already produced (never your messages or Hearth's replies). When the _same_ tool fails with the _same_ error code **5 or more times** in that window, the model is told the exact tool, error code and count (counts only, nothing else) and may call `suggest_code_change` with a short plain-text title, problem and proposal plus that exact evidence. The tool re-checks the claimed evidence against the real counter itself: a count higher than what was actually recorded, a tool/error-code pair that never reached 5, or any text that looks like code, a diff or a patch (a fenced code block, a `diff --git`/`+++`/`---` header, or an `import`/`function`/`class`-shaped line) is refused before anything is filed. Nothing here ever saves, patches or changes anything by itself.
- **In Today.** A `code` suggestion shows its title, problem, proposal and the evidence line (“`ha_state_detail` failed with `entity_not_allowed` 5 times in the last 7 days”). One touching a security-sensitive area \u2014 scope, approval, permission, credential, token, sandbox, CSP, sanitizer, risk, judge or supervisor \u2014 is labelled **Security review required** and its action is hidden behind an opened details panel and a field where you must type **CONFIRM** exactly; the server checks that confirmation itself; typing the wrong word, or getting there through any other route, is refused the same way.
- **Draft in Code session.** This is the suggestion's only action besides the existing Reject and Snooze (there is no one-tap Accept for `code`). It creates a brand-new Code session \u2014 the same offline, confined coding workspace any Code session uses, with no Home Assistant tools, no network and no provider or Home Assistant credential \u2014 and sends it one fixed message: the problem, proposal and evidence, explicitly marked as untrusted data for the worker to treat as data and never as an instruction, asking it to write the smallest correct patch plus a unit test, run the test, and end with a plain-text **PATCH SUMMARY**. If `workspace_enabled` is off, the suggestion explains that Code sessions are off instead of offering Draft; see the [workspace guide](../docs/workspace.md) to turn them on. If the draft worked, open the new Code session like any other to read the patch, the test run and the summary.
- **Releasing it.** When the Code session already exposes workspace files you can use the usual **Download**/copy from that session to get the patch out; otherwise copy the patch and test from the transcript by hand. Either way you apply it the same way as any other change to this repository: a normal commit, your own review/CI, and the add-on updates through the Supervisor like any other update. **There is no "Apply to running Hearth" button anywhere in this flow, and none exists in the code.**

Deferred: this is the simplest version of L3 from the product brief \u2014 the owner's own free-text request ("the chart is unreadable on my phone, fix it") does not yet also offer Draft in Code session, and there is no post-release "shipped in vX.Y, did the signal improve" follow-up check yet. Tested with an offline model, fake Home Assistant and fixed clocks only; real model behaviour (when and how well it recognizes the tool_health signal) is unverified, and this has not run against a real worker/operator Code session on live hardware.

## Home World (unreleased source slice)

Home World draws your home as a small pixel house, built automatically from the **Home Assistant areas** of the entities in `allowed_entities` — no setup. Each area with in-scope devices becomes a room (bigger areas get bigger rooms, HA floors become separate labelled bands); entities without an area go to an **Unassigned** shed. Furniture follows area names (kitchen, bedroom, living room, office, bathroom, garage, garden, hall) and devices get sprites by domain and device class (lights, switches, climate, fans, media players, vacuums, locks, temperature/humidity/battery sensors, doors, windows, motion sensors, printer-like sensors). Automations, people, `sun.sun` and similar entities are not drawn; at most 64 devices and 24 rooms are shown. If Hearth can't read the area registry (it needs the same HA admin token as automation traces), everything is placed in the shed with a note.

- **Everyday: the strip.** Above a Home chat a small chip summarizes the home (rooms, devices, ⚠ count). It drops into a side-view strip of the house while Hearth is thinking, or when you tap/pull it down. When a running tool call names a drawn device (for example `ha_state_detail` on a lamp), the character walks to that device's room with the caption "Reading Bedside lamp · Bedroom…". Nothing moves otherwise: no idle wandering, no animation frames while idle, drawing pauses while the page or strip is hidden, animation is capped at 30 fps and device-pixel ratio 2, and with **Reduce motion** the character simply appears where it's needed.
- **Full screen: the house.** **⤢** on the strip or **Settings → Home World** opens the top-down house with Hearth's latest exchange, a **Needs a look** list and a summary. Lights that are on glow; at night (from `sun.sun` if it is in scope, otherwise 21:00–06:00 on the App's clock) the house darkens so they stand out. Only anomalies glint: unavailable devices, a door or window open at night, a low battery (below 20 %) and leaks.
- **Devices.** Tap a device for its state, the time Hearth read it, its room/area/device and **Ask Hearth about this** (drafts a question into a Home chat; nothing is sent until you press Send). Lights and switches inside the configured `allowed_services` also get **Turn on/off**, which goes through **Home permissions** exactly like an app ToggleAction: Read-only shows it disabled with the reason, Ask opens the same exact approval card (and files it in the current Home chat, or a new "Home World" chat), Full access runs once within your grant and reads the state back. Unknown outcomes are never retried. Locks and every other domain are read-only.
- **Values.** Hearth reads the drawn devices when the strip or house opens, every 30 seconds while either is showing (paused while the page is hidden), once when a Hearth task ends and after a toggle — never while both are closed (at most 12 reads a minute). Values are controller reads with an "as of" time, not live telemetry.
- **List view.** **List** shows rooms → devices with the same state, as-of time and actions as real buttons; the map canvas is hidden from screen readers and summarized in text, and new anomalies are announced politely.
- **Edit.** **Edit** lets you drag rooms (or their corner to resize) and devices, or use the panel: rename rooms, choose a floor style, size/move with buttons, move devices between rooms, pick the character's colours and hat and turn the pet on or off. Changes are saved for you on this Hearth (a Pi Durable document per owner) with a revision check, so two open windows can't silently overwrite each other — the second one reloads. **Reset to auto layout** removes your customization. A layout saved on a device by the earlier Home World prototype is imported once (character, pet, floor styles of rooms whose names match an area and device room choices) and then deleted from the browser.

Tested with an offline model, a fake HA REST API and a fake registry WebSocket only; not yet on a real Home Assistant, the companion app's WebView or a mid-range Android for performance.

## Set up your Home World with Hearth (unreleased source slice)

Instead of dragging rooms around, ask Hearth in a Home chat: “Set up my home view” (or open **Home World → Edit → Set up with Hearth…**, which drafts that message for you to send).

1. **Hearth reads your house.** It loads its bundled _home-world-setup_ skill, reads how your home is drawn now (rooms from your Home Assistant areas, device counts, unassigned devices) and summarizes it. Then it asks whether you have a floor plan.
2. **Attach a plan.** Tap **＋** next to the message box and choose a photo, a screenshot or a screenshot of a PDF (up to 4 images per message). Your browser shrinks each image to at most 2048 px and sends it as JPEG; HEIC photos are converted by the browser when it can read them, otherwise take a screenshot. Remove an image with its ✕ before sending.
3. **Hearth asks once.** It lists the rooms it sees on the plan, maps them to your areas and asks every unclear point in one short list — labels in another language or codes, a room with two possible areas, open-plan spaces shared by two areas (kitchen + living), outdoor spaces without an area, areas that aren't physical rooms.
4. **A preview, not a change.** Hearth proposes a layout: a grid wide enough for your plan (16–40 columns), one rectangle per area, balconies, terraces or gardens as outdoor spaces (up to 8), non-physical areas and the Unassigned shed in a row below the plan, and walls shared where rooms connect (doors are drawn on every shared wall of 2 or more cells). A card in the chat shows _Home layout proposal · rooms · size_ with **Open preview**. In Home World a dashed banner marks the preview with **Keep** and **Discard**; the map and **List** show the proposal, and editing is off while you look.
5. **Keep or iterate.** **Keep** saves it as your Home World with the same checks as the editor (if Home World changed in another window meanwhile, it reloads and asks you to tap Keep again). **Discard** leaves your Home World as it was. Or keep chatting (“make the kitchen bigger”, “the balcony only runs along the living room”) — each new proposal replaces the previous one. A proposal you don't decide on expires after 7 days. After keeping, you can still edit by hand or **Reset to auto layout**.

Hearth never changes your Home Assistant areas, floors or which area a device belongs to; if something is in the wrong area it tells you where to change it in Home Assistant. Only areas of entities in `allowed_entities` are visible to it.

**Privacy.** Attached images are stored in your Hearth data on this Home Assistant (inside the chat's durable transcript) and are sent only to the model provider of that chat, as part of the conversation, on each of its requests. They are shown only to you, from Hearth itself, and are not securely erased when you delete the chat. Text written inside an image is treated as data, never as instructions. A chat whose model can't read images says so instead of sending the message (choose a model with image input from the model chip; the local OpenAI-compatible endpoint is text-only in this version). At most 12 images stay in one chat; start a new chat for more.

Tested with an offline model, a fake Home Assistant API and a fake registry only; real vision models' plan reading, iOS photo picking and the companion app were not verified.
