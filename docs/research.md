# Research and design decisions

Inspected **2026-10-03**. This is qualitative, primary-source research—not a representative survey, market-size estimate, security audit or comparison benchmark. Issues describe reports, not independently reproduced defects. Closed historical issues are useful regression-test inspiration, not evidence that a project remains broken. Public branches and issue states can change.

## Existing approaches: what we learned

| Approach                                                                                                              | Good ideas to learn from                                                                                                           | Our boundary                                                                                                                                                                                                                                                           |
| --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Official Assist/LLM API](https://developers.home-assistant.io/docs/core/llm/)                                        | Entity exposure, explicit control permissions, typed tools and contextual discovery. Assist does not provide administrative tools. | Our direct REST adapter does **not** inherit Assist exposure filtering. Exact entity scope is enforced separately. Ordinary voice control is not our target.                                                                                                           |
| [Official HA MCP Server](https://www.home-assistant.io/integrations/mcp_server/)                                      | Authenticated access, scoped Assist API and deliberate control opt-in.                                                             | Generic MCP imports, remote web content and broader administrative APIs are deferred. MCP is a transport, not a durable approval journal.                                                                                                                              |
| [Pi Agent for HA](https://github.com/dkmaker/hass-pi-agent) and [its fork](https://github.com/yazdannl/hass-pi-agent) | Ingress chat, visible setup/session controls, ARM64/amd64 support and provider onboarding.                                         | These use regular Pi, not Pi Durable. No exploit or whole-project audit is claimed. |
| [Extended OpenAI Conversation](https://github.com/jekalmin/extended_openai_conversation)                              | Configurable functions/provider choice and bounded tool rounds.                                                                    | Broad file, script, network or automation executors are outside this first release. | [Home LLM](https://github.com/acon96/home-llm)                                                                        | Local-provider choice and model/backend compatibility handling.                                                                    | Saved conversation history alone is not unfinished-task recovery. | [MCP Assist](https://github.com/mike-nott/mcp-assist)                                                                 | On-demand discovery rather than sending the whole home in every prompt.                                                            | Its advertised token reduction is its own claim. | [HA Configuration Agent](https://github.com/yinzara/ha-config-ai-agent)                                               | Reviewable diffs and the proposed validate/backup/apply/rollback sequence.                                                         | Configuration writing requires its own tested transaction/recovery design; it is not enabled here. | [Home Generative Agent](https://github.com/goruck/home-generative-agent)                                              | Deterministic allowlists, staleness checks and gating unresolved/indirect targets rather than guessing.                            | Confidence scores and in-memory deduplication are not immutable human approval or durable external-action receipts. ## Community signals and pitfalls

### Provider freedom and local privacy — recurring evidence

The [OpenAI-compatible endpoint discussion](https://community.home-assistant.io/t/wth-there-is-not-a-conversation-integration-that-let-you-use-any-openai-compatible-api/803855) (2024-12-03) asks for configurable cloud/local endpoints; replies discuss maintenance friction and existing subscriptions. This is historical demand, not a claim that today's official integrations still lack those options.

[Pi App issue #71](https://github.com/dkmaker/hass-pi-agent/issues/71), open when inspected and created 2026-09-14, requests llama.cpp support for local inference. [HA's official AI direction](https://www.home-assistant.io/blog/2025/09/11/ai-in-home-assistant/) emphasizes user choice, local processing and keeping AI out of mission-critical tasks.

**Decision:** separate provider code from HA policy. Start with a tested official OpenAI API-key adapter and explicit credential-free faux demonstration. Custom/local endpoints and subscription OAuth are next design candidates, not current capabilities. A Node agent process is not a local inference engine; the offline demonstration is not a local LLM.

### Cost, context size and latency — recurring evidence

Multiple users in [the token-cost discussion](https://community.home-assistant.io/t/new-assist-with-llm-combination-lot-of-tokens/736566) (2024-06-06) describe large context costs for simple actions. Prices and token counts are historical reports, not our benchmark. [The tool-count request](https://community.home-assistant.io/t/lets-reduce-number-of-llm-tools/872746) (2025-04-02) and replies ask for fewer overlapping tool definitions.

[Core issue #119946](https://github.com/home-assistant/core/issues/119946) is a **closed historical** 2024 report about prompts exceeding an Ollama context window, not an assertion of an outstanding Core defect.

**Decision:** a stable short prompt, four typed tools, scoped paginated discovery and selected attributes. Limit tool rounds, response sizes, active conversations and history; expose reported token usage. Search fetches a bounded HA states response internally and filters before returning results to the model—it is not an indexed HA query or a promise that no other states enter backend memory. No claimed cost/latency savings without a reproducible benchmark.

### Reviewable changes and truthful outcomes — strong safety rationale

[The Configuration Agent discussion](https://community.home-assistant.io/t/introducing-ha-configuration-agent-ai-powered-home-assistant-configuration-assistant-with-approval-workflow/944620) (2025-10-27) presents exact diffs/approval; replies question knowledge freshness and the safety of voice-driven configuration changes. An author's feature pitch alone is not community consensus.

[Extended OpenAI issue #322](https://github.com/jekalmin/extended_openai_conversation/issues/322) is a **closed historical** 2025 report of model claims that an action completed while nothing happened. We did not reproduce it or establish its current status beyond the inspected issue state.

**Decision:** a deterministic action card is the receipt of record. The model can propose but cannot approve or dispatch. Approval binds owner/session/action hash/policy/expiry. Dispatch intent is stored before one external attempt. `accepted` means an HTTP service receipt, not confirmed physical state. Timeout, crash or an error after dispatch is `unknown`; a human reconciles it without automatic retry.

### Hallucinated services and malformed arguments — concrete failure classes

[Issue #245](https://github.com/jekalmin/extended_openai_conversation/issues/245), open when inspected but originating in 2024, reports a nonexistent TTS service. [Issue #249](https://github.com/jekalmin/extended_openai_conversation/issues/249) is a **closed** 2024 report about nested-string tool arguments. These are historical/backend-specific reports, not blanket defect claims.

**Decision:** discover live service availability, validate exact entities and typed arguments, reject reserved target overrides and indirect selectors. Do not silently repair a malformed mutation into a different action. The first release permits only scoped light/switch on/off and optional light brightness; no scripts, scenes, automation triggers, areas or devices.

### Untrusted content plus physical control — explicit capability risk

[Issue #467](https://github.com/jekalmin/extended_openai_conversation/issues/467), open when inspected and created 2026-09-25, asks for documentation of external REST/scraped content sharing a context with HA service tools. This is a user-raised risk, not a demonstrated exploit or vulnerability determination.

**Decision:** no generic web/MCP/shell/file tools in the initial App. HA attributes and model outputs remain untrusted. Enforce policy outside the model, render text safely, and explain what selected data reaches the provider. Prompt instructions are not a security boundary.

### UX friction can weaken safety

[The voice-continuation discussion](https://community.home-assistant.io/t/continue-conversation-automatically-on-home-assistant-voice-pe/829487) (2025-01-15) has multiple requests for natural follow-ups. A suggested workaround disables prompt-only confirmation; another reply reports noisy-room loops. It does not establish that current Voice PE lacks continuation.

**Decision:** concise, exact, accessible action cards and browser-enforced approval flow, not confirmation solely in a system prompt. Voice/Assist integration is a separately scoped roadmap item.

### Durability is an engineering differentiator, not a proven top request

The evidence above is stronger for provider choice, cost and predictable control than for crash-durable task execution specifically. We do not claim to be the first such product or call recovery the community's top request.

[Pi Durable's official documentation](https://github.com/earendil-works/pi/tree/main/packages/durable) defines committed tasks/entries, request deduplication and safe/unsafe tool recovery. We use the actual version-pinned library and demonstrate process-death recovery. Saved chat history is not equivalent. SQLite FULL synchronization improves persistence policy but cannot establish untested hardware/power-loss guarantees or exactly-once physical effects.
