# Threat model and operational limits

Trust boundary: model output, prompts, HA attributes and tool results are untrusted. The backend controls tool registration, exact read scope, policy and action ledger. Home mode has no arbitrary shell, filesystem, config write, Supervisor admin, Docker, MCP or web-fetch tools. Optional Code mode executes genuine Pi coding tools ONLY in a separate confined offline container, never in this controller. See [worker boundaries and single-operator limitation](workspace.md). The controller is a trusted credential-bearing service, not the coding sandbox: the scoped live Supervisor target provides its UID drop/AppArmor, but not the worker's no-new-privileges/seccomp flags. Those stronger OS checks belong to the separately created worker; never move coding execution into the controller to bypass them. There is no claim that prompt instructions prevent injection. Avoid mission-critical devices and indirect controls.

Ingress mode accepts only the documented proxy socket peer `172.30.32.2` (including IPv4-mapped form) and one configured `X-Remote-User-Id`; it rejects forwarded-header identity claims. Navigation `panel_admin` does not establish authorization or current HA admin status. Authentication and ownership guard all routes, including static assets and SSE. Local mode binds loopback, requires a 24+ character password with Basic auth and ignores Ingress identity; use only on a trusted local machine. POST requires exact Origin, an HttpOnly browser cookie and bound CSRF token. Bounded headers/body/rates/streams, fixed static routes, no permissive CORS and CSP reduce exposure. Verify CSP and external-origin mobile/Ingress behavior in an isolated Supervisor setup; proxy topology differs from unit tests. TLS is the surrounding HA deployment's responsibility.

`homeassistant_api: true` grants a broad backend HA token: entity scope is app policy, not a reduction of Supervisor token privileges or inheritance of Assist exposure. Search reads the HA states endpoint before narrowing results; this may process private states in memory. Limit App users and avoid exposing sensitive entities. Service dispatch supports only exact allowed light/switch entity targets, optional brightness for light.turn_on, live service/state checks and a one-use hash/owner/expiry/policy-bound receipt. With writes configured, Ask is the default. Explicitly acknowledged Home Full access removes per-action prompts only within exact configured supported policy; untrusted model/tool content can then cause real scoped device effects. This is a deliberate opt-in risk, not protection against prompt injection. Grants are owner/revision/schema/policy-bound, cannot be set by models and cannot elevate already admitted input. Policy changes invalidate Full without resurrection. At each controller start, current configured App owners are checked and removed owners' grants are durably revoked before unfinished work resumes; re-adding an owner does not revive the old Full grant. Local mode admits only the authenticated `local-admin` identity. Authenticated settings require Origin/CSRF, bounded strict JSON and expected revision/fingerprint. Emergency Read-only invalidates pending actions and aborts/prevents dispatch without waiting for HA, but cannot undo attempted effects. Durable pending-dispatch/unknown outcomes block all Home writes installation-wide across owners/conversations/mode toggles/restart; only explicit owner reconciliation clears the specific unknown. Tools are unsafe to replay, and fresh autonomous reissue is blocked while uncertainty persists. Code remains separately confined and unchanged. No device/area/group/scene/script/automation selector. HA service receipt cannot prove a real-world effect; timeout, crash, network or even HTTP error after dispatch may mean unknown. Human reconciliation must use independent observation before deciding whether to create a new proposal. Do not restore backups and assume the external world rolled back.

Configured raw credentials are redacted before input/title admission and human resolution-note persistence; credentials in idempotency keys are rejected. Provider/HA outputs and API responses also redact known secrets. This is not detection of arbitrary secrets or every encoding—never put credentials in chat. Provider key and Supervisor token are not exposed as tools or API metadata. Nonetheless transcripts, selected tool results and service proposals persist on `/data`; Online API-key/Codex mode transmits inputs/context/tool schemas/selected HA or explicitly read coding output to OpenAI; flagged Anthropic mode transmits them to Anthropic. Anthropic login/transport is experimental and disabled by default. Provider terms, account eligibility and extra per-token billing may apply; included Claude-plan usage is not guaranteed. Exact env `HEARTH_ANTHROPIC_AUTH_ENABLED=true` (or the typed HA option when env is absent) opts in without changing provider, scope, permissions or worker confinement. A selected Anthropic provider with flag off fails closed. Only the pinned compatibility transport helper is loaded; no ambient extension factory/config/account diagnostics/debug metadata. Separate Anthropic/Codex `0600` credential files and serialized refresh preserve isolation. Copy-code/manual callbacks require complete code/state, exact callback origin and current PKCE state. `/login` is human auth, intercepted before transcript/input admission; mismatched providers cannot switch the running model. Official subscription OAuth uses protected controller storage, serialized refresh and owner-bound temporary login state; access/refresh tokens never go to the worker or browser/model metadata. Authorized App IDs are trusted operators of the installation's shared provider setup; they are not untrusted tenants. Device codes/PKCE redirect URLs are ephemeral human-login material, not chat/tool data, and must not be shared or recorded. `store:false` is requested but provider retention/billing remains subject to provider policy. Treat options, SQLite and backups as sensitive; cold backup is not a cryptographic rollback of actions. SQLite FULL and local SIGKILL recovery are not physical power-loss assurance, exactly-once effects, cross-process distributed locking or an external security audit. One local store owner is enforced via SQLite exclusive locking; use local storage. Disable actions and coding by default. Worker startup rejects missing namespace/confinement invariants; the App cannot create/manage its Docker container. OS evidence must be verified on the real target. Workspace files need separate backups; interrupted coding calls and uncertain turns require fresh human input, not automatic reissue. Unreleased `local` provider: only an authorized owner can save an endpoint; Hearth contacts only the URL entered (no scanning), requires private/loopback/unique-local addresses for every resolved address, refuses link-local/metadata ranges, the `supervisor` host and 172.30.32.2, and does not follow redirects. DNS may change after the check, so this is an operator guard, not an SSRF guarantee against hostile DNS. Conversation context and selected Home data go to that server. Server responses are untrusted: model ids are pattern-checked and sizes/counts bounded. An optional key is stored `0600` in controller `/data`, redacted from output, and restricted to plain token characters because Pi treats `!`/`$` prefixes as commands/environment references. Report vulnerabilities via [SECURITY.md](../SECURITY.md).

Apps (HAS/1, unreleased): model-written app specs are untrusted data, never code. The controller validates them against a fixed component catalog before storing (unknown types/props, markup/script-like text, cycles/orphans/limits, literal values in entity-bound props, entities outside `scope.entities` or the configured read scope, ToggleActions outside the configured exact light/switch services are rejected) and revalidates on every update, revert, read and press. The browser renders only catalog components with `textContent`/DOM APIs under the existing CSP (`script-src 'self'`, no inline script/style), so spec text, HA names/states and household notes cannot inject markup or script; unknown or malformed blocks render as an “Unsupported block”. Every displayed value is a controller read with its observation time; a spec can never supply a value, URL, style or callback. Model tools can create/update/read apps but have no path to press controls, tick checklists or edit household data, and they exist only in Home conversations (never Code). ToggleAction presses are authenticated, Origin/CSRF-checked owner requests that pick the service from a fresh state read and then enter the same Home permissions broker and action ledger as model proposals: Read-only denies before any HA request, Ask files an exact proposal for human approval, Full dispatches once within the current owner/revision/policy-bound grant; unknown outcomes are never retried and block Home writes installation-wide until human reconciliation. AskButton drafts text only. App reads are rate-limited and bounded (24 scope entities, 2 charts × 3 entities × 48 h, 2 MB HA responses, 48 points). Apps are owner-scoped like sessions; deletion retires documents but does not securely erase committed history. Checklist items and notes typed by household members are untrusted if later shown to a model.

Automation troubleshooting (unreleased, read-only): Home conversations get four read tools for automation entities that are themselves in the exact configured read scope. Config is read with REST `GET /api/config/automation/config/<id>` (HA also serves POST/DELETE on that path; Hearth's reader is constructed with a GET-only function and a static test rejects write verbs, `fetch` and service paths in the new code). Traces need HA's WebSocket API: a minimal client connects to `ws://supervisor/core/websocket`, authenticates with the Supervisor token and can send only `auth`, `trace/list` and `trace/get` through one allowlisted send function — other types (e.g. `call_service`, `execute_script`, `subscribe_events`) are refused before a frame is written. Sessions are short-lived, with a 10 s deadline, 1 MB per frame, 4 MB per session and 8 commands; frame text is redacted before parsing. Both endpoints require HA admin; the broad Supervisor token is not narrowed by this feature, so policy is enforced by Hearth's fixed tools. Residual risks: (1) trace and config text are untrusted and could carry prompt injection — they are returned as data, scrubbed and size-bounded, and the model has no tool that can change configuration; (2) traces capture values of any entity the automation touched — trigger states are shown only for in-scope entities, other entities referenced by the config are named as outside the read scope and not read, and condition observations/rendered action data are withheld whenever any reference is outside scope, a device ID or an indirect template, but detection of references is pattern-based; (3) secrets resolved into configs/traces (from `!secret` or literal values) are only removed by configured-secret redaction plus key/URL/bearer/JWT patterns, so an unusual secret format may survive — keep such automations out of `allowed_entities` if in doubt; (4) drafted YAML is model output the owner must review before pasting; Hearth cannot apply it.
