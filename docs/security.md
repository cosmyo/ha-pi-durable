# Threat model and operational limits

Trust boundary: model output, prompts, HA attributes and tool results are untrusted. The backend controls tool registration, exact read scope, policy and action ledger. Home mode has no arbitrary shell, filesystem, config write, Supervisor admin, Docker, MCP or web-fetch tools. Optional Code mode executes genuine Pi coding tools ONLY in a separate confined offline container, never in this controller. See [worker boundaries and single-operator limitation](workspace.md). The controller is a trusted credential-bearing service, not the coding sandbox: the scoped live Supervisor target provides its UID drop/AppArmor, but not the worker's no-new-privileges/seccomp flags. Those stronger OS checks belong to the separately created worker; never move coding execution into the controller to bypass them. There is no claim that prompt instructions prevent injection. Avoid mission-critical devices and indirect controls.

Ingress mode accepts only the documented proxy socket peer `172.30.32.2` (including IPv4-mapped form) and one configured `X-Remote-User-Id`; it rejects forwarded-header identity claims. Navigation `panel_admin` does not establish authorization or current HA admin status. Authentication and ownership guard all routes, including static assets and SSE. Local mode binds loopback, requires a 24+ character password with Basic auth and ignores Ingress identity; use only on a trusted local machine. POST requires exact Origin, an HttpOnly browser cookie and bound CSRF token. Bounded headers/body/rates/streams, fixed static routes, no permissive CORS and CSP reduce exposure. Verify CSP and external-origin mobile/Ingress behavior in an isolated Supervisor setup; proxy topology differs from unit tests. TLS is the surrounding HA deployment's responsibility.

`homeassistant_api: true` grants a broad backend HA token: entity scope is app policy, not a reduction of Supervisor token privileges or inheritance of Assist exposure. Search reads the HA states endpoint before narrowing results; this may process private states in memory. Limit App users and avoid exposing sensitive entities. Service dispatch supports only exact allowed light/switch entity targets, optional brightness for light.turn_on, live service/state checks and a one-use hash/owner/expiry/policy-bound receipt. With writes configured, Ask is the default. Explicitly acknowledged Home Full access removes per-action prompts only within exact configured supported policy; untrusted model/tool content can then cause real scoped device effects. This is a deliberate opt-in risk, not protection against prompt injection. Grants are owner/revision/schema/policy-bound, cannot be set by models and cannot elevate already admitted input. Policy changes invalidate Full without resurrection. At each controller start, current configured App owners are checked and removed owners' grants are durably revoked before unfinished work resumes; re-adding an owner does not revive the old Full grant. Local mode admits only the authenticated `local-admin` identity. Authenticated settings require Origin/CSRF, bounded strict JSON and expected revision/fingerprint. Emergency Read-only invalidates pending actions and aborts/prevents dispatch without waiting for HA, but cannot undo attempted effects. Durable pending-dispatch/unknown outcomes block all Home writes installation-wide across owners/conversations/mode toggles/restart; only explicit owner reconciliation clears the specific unknown. Tools are unsafe to replay, and fresh autonomous reissue is blocked while uncertainty persists. Code remains separately confined and unchanged. No device/area/group/scene/script/automation selector. HA service receipt cannot prove a real-world effect; timeout, crash, network or even HTTP error after dispatch may mean unknown. Human reconciliation must use independent observation before deciding whether to create a new proposal. Do not restore backups and assume the external world rolled back.

Configured raw credentials are redacted before input/title admission and human resolution-note persistence; credentials in idempotency keys are rejected. Provider/HA outputs and API responses also redact known secrets. This is not detection of arbitrary secrets or every encoding—never put credentials in chat. Provider key and Supervisor token are not exposed as tools or API metadata. Nonetheless transcripts, selected tool results and service proposals persist on `/data`; Online API-key/Codex mode transmits inputs/context/tool schemas/selected HA or explicitly read coding output to OpenAI; flagged Anthropic mode transmits them to Anthropic. Anthropic login/transport is experimental and disabled by default. Provider terms, account eligibility and extra per-token billing may apply; included Claude-plan usage is not guaranteed. Exact env `HEARTH_ANTHROPIC_AUTH_ENABLED=true` (or the typed HA option when env is absent) opts in without changing provider, scope, permissions or worker confinement. A selected Anthropic provider with flag off fails closed. Only the pinned compatibility transport helper is loaded; no ambient extension factory/config/account diagnostics/debug metadata. Separate Anthropic/Codex `0600` credential files and serialized refresh preserve isolation. Copy-code/manual callbacks require complete code/state, exact callback origin and current PKCE state. `/login` is human auth, intercepted before transcript/input admission; mismatched providers cannot switch the running model. Official subscription OAuth uses protected controller storage, serialized refresh and owner-bound temporary login state; access/refresh tokens never go to the worker or browser/model metadata. Authorized App IDs are trusted operators of the installation's shared provider setup; they are not untrusted tenants. Device codes/PKCE redirect URLs are ephemeral human-login material, not chat/tool data, and must not be shared or recorded. `store:false` is requested but provider retention/billing remains subject to provider policy. Treat options, SQLite and backups as sensitive; cold backup is not a cryptographic rollback of actions. SQLite FULL and local SIGKILL recovery are not physical power-loss assurance, exactly-once effects, cross-process distributed locking or an external security audit. One local store owner is enforced via SQLite exclusive locking; use local storage. Disable actions and coding by default. Worker startup rejects missing namespace/confinement invariants; the App cannot create/manage its Docker container. OS evidence must be verified on the real target. Workspace files need separate backups; interrupted coding calls and uncertain turns require fresh human input, not automatic reissue. Unreleased `local` provider: only an authorized owner can save an endpoint; Hearth contacts only the URL entered (no scanning), requires private/loopback/unique-local addresses for every resolved address, refuses link-local/metadata ranges, the `supervisor` host and 172.30.32.2, and does not follow redirects. DNS may change after the check, so this is an operator guard, not an SSRF guarantee against hostile DNS. Conversation context and selected Home data go to that server. Server responses are untrusted: model ids are pattern-checked and sizes/counts bounded. An optional key is stored `0600` in controller `/data`, redacted from output, and restricted to plain token characters because Pi treats `!`/`$` prefixes as commands/environment references. Report vulnerabilities via [SECURITY.md](../SECURITY.md).

Apps (HAS/1, unreleased): model-written app specs are untrusted data, never code. The controller validates them against a fixed component catalog before storing (unknown types/props, markup/script-like text, cycles/orphans/limits, literal values in entity-bound props, entities outside `scope.entities` or the configured read scope, ToggleActions outside the configured exact light/switch services are rejected) and revalidates on every update, revert, read and press. The browser renders only catalog components with `textContent`/DOM APIs under the existing CSP (`script-src 'self'`, no inline script/style), so spec text, HA names/states and household notes cannot inject markup or script; unknown or malformed blocks render as an “Unsupported block”. Every displayed value is a controller read with its observation time; a spec can never supply a value, URL, style or callback. Model tools can create/update/read apps but have no path to press controls, tick checklists or edit household data, and they exist only in Home conversations (never Code). ToggleAction presses are authenticated, Origin/CSRF-checked owner requests that pick the service from a fresh state read and then enter the same Home permissions broker and action ledger as model proposals: Read-only denies before any HA request, Ask files an exact proposal for human approval, Full dispatches once within the current owner/revision/policy-bound grant; unknown outcomes are never retried and block Home writes installation-wide until human reconciliation. AskButton drafts text only. App reads are rate-limited and bounded (24 scope entities, 2 charts × 3 entities × 48 h, 2 MB HA responses, 48 points). Apps are owner-scoped like sessions; deletion retires documents but does not securely erase committed history. Checklist items and notes typed by household members are untrusted if later shown to a model.

Household memory and suggestions (unreleased, L1/L2): memory items are owner-entered or owner-accepted plain text (one line, ≤200 characters, credential-redacted), stored per owner in a Pi Durable document written only by that owner's authenticated, Origin/CSRF-checked requests. They reach Home prompts in a separate `household_memory` section marked OWNER-APPROVED CONTEXT that states it never grants permissions, widens scope or overrides safety rules; angle/square brackets are replaced and line breaks removed so item text cannot close the section tag or forge its BEGIN/END markers, and at most 4 KB is included (oldest trimmed first). This is a prompt-level boundary, not a guarantee against injection: memory text is treated as untrusted data like any other content, and every permission is still enforced by the controller (Home permissions broker, exact scopes), never by prompt text. Forget removes an item from the document and later prompts but is not a secure erase (committed document history and earlier prompt entries in existing transcripts remain in `/data`). Model tools `suggest_memory` and `suggest_app_change` exist only in Home conversations and only create proposals; the proposal schema has exactly two kinds (`memory`, `app_change`), with no field or kind that can touch Home permissions, entity/service scope, credentials, providers or settings (unit-tested), and app patches pass the same full HAS/1 validation as `app_update` at proposal and acceptance time. Acceptance is an owner UI request bound to the proposal hash and recorded with the owner's ID; an app change applies only at its base version (otherwise a recorded conflict). Rejections suppress the same normalized text or patch hash for 60 days; proposals are rate-limited per conversation and per owner per day. After a 👎 with reasons in an app-building conversation, the next owner turn gets an `owner_feedback` section with message ids and reason enums only; nothing runs in the background.
Automation troubleshooting (unreleased, read-only): Home conversations get four read tools for automation entities that are themselves in the exact configured read scope. Config is read with REST `GET /api/config/automation/config/<id>` (HA also serves POST/DELETE on that path; Hearth's reader is constructed with a GET-only function and a static test rejects write verbs, `fetch` and service paths in the new code). Traces need HA's WebSocket API: a minimal client connects to `ws://supervisor/core/websocket`, authenticates with the Supervisor token and can send only `auth`, `trace/list`, `trace/get` and the three read-only registry lists used by Home World (`config/area_registry/list`, `config/device_registry/list`, `config/entity_registry/list`) through one allowlisted send function; registry create/update/delete, floor/label registries and all other types (e.g. `call_service`, `execute_script`, `subscribe_events`) are refused before a frame is written. Sessions are short-lived, with a 10 s deadline, 1 MB per frame, 4 MB per session and 8 commands; frame text is redacted before parsing. Both endpoints require HA admin; the broad Supervisor token is not narrowed by this feature, so policy is enforced by Hearth's fixed tools. Residual risks: (1) trace and config text are untrusted and could carry prompt injection — they are returned as data, scrubbed and size-bounded, and the model has no tool that can change configuration; (2) traces capture values of any entity the automation touched — trigger states are shown only for in-scope entities, other entities referenced by the config are named as outside the read scope and not read, and condition observations/rendered action data are withheld whenever any reference is outside scope, a device ID or an indirect template, but detection of references is pattern-based; (3) secrets resolved into configs/traces (from `!secret` or literal values) are only removed by configured-secret redaction plus key/URL/bearer/JWT patterns, so an unusual secret format may survive — keep such automations out of `allowed_entities` if in doubt; (4) drafted YAML is model output the owner must review before pasting; Hearth cannot apply it.

Home World (unreleased): the house is generated by the controller from the area, device and entity registries, read over the same allowlisted WebSocket client (only the three `…/list` types; registry sessions allow 3 commands, 8 MB per frame, 16 MB total and a 10 s deadline, cached for 5 minutes). The registries are broad, so the reply is projected immediately to the entities in `allowed_entities`: only their area id/name/floor id and device display name are kept; other entities, config entries, unique ids, pictures, aliases and labels are discarded before anything reaches the browser or a model (tests assert this). Names are redacted and length-bounded and rendered with `textContent` only. Device values are the existing scoped state reads, rate-limited per owner. World toggles accept only drawn light/switch entities with both on/off services configured, choose the service from a fresh read and enter the same Home permissions broker and action ledger as app ToggleActions (origin `world`): Read-only denies before any HA request, Ask files an exact proposal for human approval, Full access dispatches once within the owner's grant; unknown outcomes block writes and are never retried. Think-mode motion is derived only from the durable `pi.live` tool round and a call's `entityId` argument; the world modules make no requests of their own (app.js passes request helpers) and use no `innerHTML`/`eval` (static test). Owner customization is a strictly validated Pi Durable document (bounded rooms/devices, no unknown keys, in-scope entities only) with optimistic concurrency; like other documents it is not securely erased on reset. The one-time prototype import accepts only the old schema and never repairs invalid input.

Admin access mode (unreleased, owner opt-in via `access_mode: admin` in the App configuration only): Hearth reads every entity, registry and automation/script/scene config and allowlisted Supervisor information, and can propose any service call, config write/delete, allowlisted registry/helper WebSocket mutation and allowlisted Supervisor action. Threats and controls: (1) **prompt injection** through entity names, attributes, automation/trace text, add-on names or logs can steer the conversation model into proposing harmful changes — every mutation is an exact durable proposal classified by deterministic controller rules (`src/risk.ts`) that never read model or tool text and fail closed: whenever the classifier cannot see what an action would do it rates it high, never lower — every automation/script write is at least high (a stored automation can later act without a person) and critical when its serialized body mentions a critical service in any form (templates, any letter case, beyond any item count); scenes are rated by their member domains (`scene.turn_on` by the live `entity_id` attribute of the target scene), covers by one live read of every target (missing, unreadable, door/garage/gate, or device/area targets → high), `update.*` on Core/OS/Supervisor or unverifiable update targets → critical, renaming/hiding a cover/lock/alarm/siren/camera → high, and self-protection applies to every domain's targets (Hearth's slug, Supervisor-reported name, entities); Full access auto-runs only low risk (medium only with an agreeing judge), high and critical always need exact human approval, and Ask/Read-only behave as before; (2) the **risk judge** is a separate tool-less call that sees only the owner's latest message, the exact action JSON and the deterministic level, plus at most the last 4 prior exchanges (earlier owner requests, earlier exact actions, its own verdicts) of an in-memory per-owner/per-conversation/per-model session (TTL default 5 minutes, never durable); it never sees tool output, entity attributes, logs, memory or secrets (canary-tested), it can only escalate or flag a mismatch, and any error, timeout or garbage fails closed to Ask — a compromised judge can make Hearth ask more, never less; (3) **critical confirmations** (host power, backup restore/remove, add-on uninstall, system updates, self-targeting) require a typed word in addition to approval, checked server-side; (4) **self-protection**: actions that stop, reconfigure, update or uninstall Hearth's own add-on, or configs referring to it, are critical; (5) Supervisor access goes directly to Supervisor's own REST API (`http://supervisor/<path>`, `Authorization: Bearer $SUPERVISOR_TOKEN`) rather than through Home Assistant Core: Core's `supervisor/api` WebSocket command rejects the add-on's Supervisor-proxied connection with `{"code":"unauthorized"}` because it is not an HA admin user (verified against a real Home Assistant 2026.9 / current Supervisor install). The manifest grants the add-on's token Supervisor's **manager** role (`hassio_api: true`, `hassio_role: manager`) in **every installation**, not just admin-mode ones; **manager is broad** — Supervisor's own role table (`api/middleware/security.py`) gives it every endpoint Hearth allowlists below and nearly everything else except an add-on's own protection-mode toggle, OS datadisk wipe and host SSH authorized-keys, so **Hearth's fixed, re-checked-before-every-send path allowlists and safe-field projections are the actual enforcement boundary, not the token's role**; a compromise of the controller process could use the full manager role, including endpoints Hearth itself never calls. Hearth never requests `hassio_role: admin`. Scoped mode never registers or calls a Supervisor tool regardless of the token's role — enforced in code (`src/ha.ts`), checked before any network call. Mutations distinguish a definite pre-handler 4xx (token/role/shape rejected, nothing happened: reported **failed**, not retried) from a network error, timeout or 5xx after the request may have reached Supervisor's handler (reported **unknown**, blocking Home writes installation-wide until a human reconciles it, same as every other action kind, never retried either way); no redirect is ever followed, responses are size-capped, and backup create/restore and add-on install/update ask Supervisor to queue a background job instead of holding the request open. Still no host shell, filesystem or Docker; (6) Supervisor info reaches the model only through per-endpoint safe-field allowlists (never add-on options/schema, network maps, ingress entry URLs or backup protection details), admin entity attributes are bounded (≤40 keys, ≤200 characters, secret-like keys, nested objects and tokenized picture URLs dropped), and logs and config text are redacted (configured secrets plus bearer/JWT/`sk-`/password-shaped values) and capped, which is not detection of every secret format; (7) an optional `endpoint/` judge server receives the owner's request and action JSON, must be on a private address (re-checked each call, no redirects) and its key is redacted like other secrets. Unknown outcomes of every action kind block Home writes installation-wide until human reconciliation and are never retried. Admin mode trades least privilege for convenience; prefer Ask.

Admin mode residual risks (inherent limits of rule-based classification): the classifier rates by domain, service, targets and live attributes, not by what a device physically does. A `switch.*` (or `light.*`) entity that actually drives a lock, gate or garage relay, with an innocuous name and no opening device class, is rated low like any comfort switch and can auto-run under Full access. Owners who have such relays should give them a revealing name or device class, keep Home permissions on Ask, or stay in Scoped mode. `automation.turn_on/off` and other medium-rated service calls on existing automations rely on the automation body having been gated at high or critical when it was written; automations created outside Hearth were never classified by it. The judge is a second opinion only: it can escalate or flag a mismatch, never approve, and a misjudgment can at most leave a medium action that the deterministic rules allowed.
Image attachments and Home World setup (unreleased): owners can attach up to 4 images to a Home chat message (for example a floor-plan photo). The browser re-encodes each to JPEG of at most 2048 px; the server does not trust that: it decodes strict base64, identifies the type by magic bytes (JPEG, PNG and WebP only; HEIC/HEIF/AVIF, SVG, GIF and anything else are refused, and a declared type that disagrees with the bytes is refused), and bounds each image to 4 MB and 4096 px per side, a message to 10 MB and a conversation's active transcript to 12 images. The inputs request body may be up to 14 MB and the server's request timeout is 60 s (other bodies keep their 8–32 KB limits and 5 s read deadline). Images are stored inside the durable Pi user message (Pi Durable's `UserInput` carries pi-ai `ImageContent`); the controller's inputs document holds them only until the message is placed. Session snapshots and SSE carry only a reference; bytes are served by `GET /api/sessions/<id>/images/<entry>/<n>`, which is authenticated, owner-checked through the session like every session route, re-identifies the bytes, sets the image type explicitly with `nosniff`, and is privately cacheable. CSP allows images from `'self'` and `blob:` (for the composer's local thumbnails) only. Images go to the session's model provider as part of the conversation context on every request in that chat, and nowhere else. A session whose model does not accept image input refuses the message (409 `model_no_image_input`) instead of silently dropping the image. Images are untrusted input: text inside an image is data, never instructions, and the system prompt says so — this is a prompt-level statement, not a guarantee against injection; every permission is still enforced by the controller. Like transcripts, images are not securely erased by deleting a session.

Bundled skills (`hearth_pi/skills/<name>/SKILL.md`) are repository content, reviewed like code, packaged read-only into the image and loaded once at startup with strict frontmatter and a 24 KB limit. Home prompts list only their names and descriptions; `hearth_skill` returns one skill's text by looking the name up in that fixed set (a strict name pattern; no path is ever built from model input), and no tool can write or add a skill. The Home World setup tools read the same scoped registry projection as the Home World routes (`world_layout_get`, bounded output) and `world_layout_propose` only stores a validated per-owner draft (one per owner, 7-day expiry) in the Home World layouts document without touching the saved layout or its revision. Keeping a draft is an authenticated, Origin/CSRF-checked owner request with the draft id and the saved layout's revision, revalidated exactly like an editor save; Discard is the same kind of request. No tool changes Home Assistant areas, floors, devices or any configuration.
Admin access mode (unreleased, owner opt-in via `access_mode: admin` in the App configuration only): Hearth reads every entity, registry and automation/script/scene config and allowlisted Supervisor information, and can propose any service call, config write/delete, allowlisted registry/helper WebSocket mutation and allowlisted Supervisor action. Threats and controls: (1) **prompt injection** through entity names, attributes, automation/trace text, add-on names or logs can steer the conversation model into proposing harmful changes — every mutation is an exact durable proposal classified by deterministic controller rules (`src/risk.ts`) that never read model or tool text; Full access auto-runs only low risk (medium only with an agreeing judge), high and critical always need exact human approval, and Ask/Read-only behave as before; (2) the **risk judge** is a separate tool-less call that sees only the owner's latest message, the exact action JSON and the deterministic level, plus its own prior verdicts in an in-memory per-owner/per-conversation/per-model session (≤12 exchanges, TTL default 5 minutes, never durable); it never sees tool output, entity attributes, logs, memory or secrets (canary-tested), it can only escalate or flag a mismatch, and any error, timeout or garbage fails closed to Ask — a compromised judge can make Hearth ask more, never less; (3) **critical confirmations** (host power, backup restore/remove, add-on uninstall, system updates, self-targeting) require a typed word in addition to approval, checked server-side; (4) **self-protection**: actions that stop, reconfigure, update or uninstall Hearth's own add-on, or configs referring to it, are critical; (5) Supervisor access goes through Core's `supervisor/api` WebSocket proxy with explicit endpoint allowlists checked at validation and again right before sending (verified only against fakes; Core's own admin check applies), with no manifest Supervisor role, host shell, filesystem or Docker; (6) logs and config text are redacted (configured secrets plus bearer/JWT/`sk-`/password-shaped values) and capped, which is not detection of every secret format; (7) an optional `endpoint/` judge server receives the owner's request and action JSON, must be on a private address (re-checked each call, no redirects) and its key is redacted like other secrets. ## Local risk judge

The risk judge described above (point 2) is optional and, by design, can only **escalate** a deterministic risk level or flag a mismatch — never lower a level, never approve a mutation, never act. The experimental **Hearth Judge** add-on (`hearth_judge/`) is one way to run it: a small open-weight model served by the official `ghcr.io/ggml-org/llama.cpp` server, on the same Home Assistant host, reachable only on the internal `hassio` network (no `ports:`, no ingress, no `homeassistant_api`/`hassio_api`). Choosing it (`risk_judge_model: endpoint/<model>`, `risk_judge_url` pointed at the add-on) keeps the owner's latest message and the exact proposed action JSON on the host for judging, instead of sending them to a cloud provider; the conversation model itself still sees them, as always, and classification itself is still the deterministic floor (`src/risk.ts`), never the judge. Hearth Judge never reads Home Assistant state, never gets a Supervisor or HA token, and its optional `api_key` only protects that one endpoint. Its model is downloaded once and sha256-verified against a pin recorded in `hearth_judge/models.json`; `run.sh` refuses to start if that pin is missing or malformed. A tiny local model is expected to be a weaker judge than a cloud one — run [the evaluation harness](../hearth_pi/eval/) (false-agree rate and escalation recall especially) before relying on it for anything beyond low-risk actions, and keep `risk_judge_timeout_ms` above its measured p95 latency so a slow reply fails closed to Ask instead of silently "no agreement". See [hearth_judge/DOCS.md](../hearth_judge/DOCS.md) for its own threat notes (non-root process, writable surface limited to `/data`, no declarative read-only-rootfs option in this add-on's manifest).
