# Threat model and operational limits

Trust boundary: model output, prompts, HA attributes and tool results are untrusted. The backend controls tool registration, exact read scope, policy and action ledger. Home mode has no arbitrary shell, filesystem, config write, Supervisor admin, Docker, MCP or web-fetch tools. Optional Code mode executes genuine Pi coding tools ONLY in a separate confined offline container, never in this controller. See [worker boundaries and the shared-workspace owner limitation](workspace.md). The controller is a trusted credential-bearing service, not the coding sandbox: the scoped live Supervisor target provides its UID drop/AppArmor, but not the worker's no-new-privileges/seccomp flags. Those stronger OS checks belong to the separately created worker; never move coding execution into the controller to bypass them. There is no claim that prompt instructions prevent injection. Avoid mission-critical devices and indirect controls.

Ingress mode accepts only the documented proxy socket peer `172.30.32.2` (including IPv4-mapped form) and one configured `X-Remote-User-Id`; it rejects forwarded-header identity claims. Navigation `panel_admin` does not establish authorization or current HA admin status; the manifest sets it to `false` so non-admin household members can open the panel at all (to be verified on a live install), which does not widen access: every request still needs an authorized `X-Remote-User-Id`. Authentication and ownership guard all routes, including static assets and SSE. Local mode binds loopback, requires a 24+ character password with Basic auth and ignores Ingress identity; use only on a trusted local machine. POST requires exact Origin, an HttpOnly browser cookie and bound CSRF token. Bounded headers/body/rates/streams, fixed static routes, no permissive CORS and CSP reduce exposure. Verify CSP and external-origin mobile/Ingress behavior in an isolated Supervisor setup; proxy topology differs from unit tests. TLS is the surrounding HA deployment's responsibility.

`homeassistant_api: true` grants a broad backend HA token: entity scope is app policy, not a reduction of Supervisor token privileges or inheritance of Assist exposure. Search reads the HA states endpoint before narrowing results; this may process private states in memory. Limit App users and avoid exposing sensitive entities. Service dispatch supports only exact allowed light/switch entity targets, optional brightness for light.turn_on, live service/state checks and a one-use hash/owner/expiry/policy-bound receipt. With writes configured, Ask is the default. Explicitly acknowledged Home Full access removes per-action prompts only within exact configured supported policy; untrusted model/tool content can then cause real scoped device effects. This is a deliberate opt-in risk, not protection against prompt injection. Grants are owner/revision/schema/policy-bound, cannot be set by models and cannot elevate already admitted input. Policy changes invalidate Full without resurrection. At each controller start, current configured App owners are checked and removed owners' grants are durably revoked before unfinished work resumes; re-adding an owner does not revive the old Full grant. Local mode admits only the authenticated `local-admin` identity. Authenticated settings require Origin/CSRF, bounded strict JSON and expected revision/fingerprint. Emergency Read-only invalidates pending actions and aborts/prevents dispatch without waiting for HA, but cannot undo attempted effects. Durable pending-dispatch/unknown outcomes pause new Home writes to the same entities (targets plus group members read by the controller) across owners/conversations/mode toggles/restart; an unknown whose action can reach anything (configuration, registry, Supervisor, scripts, scenes, automations, device/area targets, other domains, a target that could not be read, older receipts without a recorded scope) and any such new action pause every write. A new proposal for a paused entity is refused, so an uncertain action is never reissued; only explicit owner reconciliation or read-only reconciliation from Home Assistant state (below) clears the specific unknown. Tools are unsafe to replay, and fresh autonomous reissue is blocked while uncertainty persists. Code remains separately confined and unchanged. No device/area/group/scene/script/automation selector. HA service receipt cannot prove a real-world effect; timeout, crash, network or even HTTP error after dispatch may mean unknown. Human reconciliation must use independent observation before deciding whether to create a new proposal. Do not restore backups and assume the external world rolled back.

Configured raw credentials are redacted before input/title admission and human resolution-note persistence; credentials in idempotency keys are rejected. Provider/HA outputs and API responses also redact known secrets. This is not detection of arbitrary secrets or every encoding—never put credentials in chat. Provider key and Supervisor token are not exposed as tools or API metadata. Nonetheless transcripts, selected tool results and service proposals persist on `/data`; Online API-key/Codex mode transmits inputs/context/tool schemas/selected HA or explicitly read coding output to OpenAI; flagged Anthropic mode transmits them to Anthropic. Anthropic login/transport is experimental and disabled by default. Provider terms, account eligibility and extra per-token billing may apply; included Claude-plan usage is not guaranteed. Exact env `HEARTH_ANTHROPIC_AUTH_ENABLED=true` (or the typed HA option when env is absent) opts in without changing provider, scope, permissions or worker confinement. A selected Anthropic provider with flag off fails closed. Only the pinned compatibility transport helper is loaded; no ambient extension factory/config/account diagnostics/debug metadata. Separate Anthropic/Codex `0600` credential files and serialized refresh preserve isolation. Copy-code/manual callbacks require complete code/state, exact callback origin and current PKCE state. `/login` is human auth, intercepted before transcript/input admission; mismatched providers cannot switch the running model. Official subscription OAuth uses protected controller storage, serialized refresh and owner-bound temporary login state; access/refresh tokens never go to the worker or browser/model metadata. Authorized App IDs are trusted members of one household, not untrusted tenants. Household roles (unreleased; `member_user_ids`, `guest_user_ids`, App configuration only, validated at startup) narrow them: only owners may log in, log out or configure the shared provider credential and local endpoint (`/api/auth/*`, `/api/local/*` writes and `/login` return `403 role_requires_owner` otherwise); members are limited to Read-only/Ask (`role_forbids_full`, an existing Full grant is downgraded at startup) and to low/medium risk, checked after judge escalation at proposal/press/undo admission and again inside the dispatch authorization (`role_requires_owner`); guests are Read-only, refused before any Home Assistant request (`role_guest_read_only`), get no proposal, suggestion, memory-write, app-edit, watcher, Phone-approval or admin/automation-read tools or routes, and never receive household memory in prompts or API responses. Tools are offered per role through separate Home extension groups re-applied at every start, and every Home tool re-checks the session owner's current role when it runs. A role change bumps the Home permissions revision, so pending proposals go stale. Guests still see whatever the read scope exposes; roles are not isolation between untrusted tenants. Device codes/PKCE redirect URLs are ephemeral human-login material, not chat/tool data, and must not be shared or recorded. `store:false` is requested but provider retention/billing remains subject to provider policy. Treat options, SQLite and backups as sensitive; cold backup is not a cryptographic rollback of actions. SQLite FULL and local SIGKILL recovery are not physical power-loss assurance, exactly-once effects, cross-process distributed locking or an external security audit. One local store owner is enforced via SQLite exclusive locking; use local storage. Disable actions and coding by default. Worker startup rejects missing namespace/confinement invariants; the App cannot create/manage its Docker container. OS evidence must be verified on the real target. Workspace files need separate backups; interrupted coding calls and uncertain turns require fresh human input, not automatic reissue. Unreleased `local` provider: only an authorized owner can save an endpoint; Hearth contacts only the URL entered (no scanning), requires private/loopback/unique-local addresses for every resolved address, refuses link-local/metadata ranges, the `supervisor` host and 172.30.32.2, and does not follow redirects. DNS may change after the check, so this is an operator guard, not an SSRF guarantee against hostile DNS. Conversation context and selected Home data go to that server. Server responses are untrusted: model ids are pattern-checked and sizes/counts bounded. An optional key is stored `0600` in controller `/data`, redacted from output, and restricted to plain token characters because Pi treats `!`/`$` prefixes as commands/environment references. Report vulnerabilities via [SECURITY.md](../SECURITY.md).

Apps (HAS/1, unreleased): model-written app specs are untrusted data, never code. The controller validates them against a fixed component catalog before storing (unknown types/props, markup/script-like text, cycles/orphans/limits, literal values in entity-bound props, entities outside `scope.entities` or the configured read scope, ToggleActions outside the configured exact light/switch services are rejected) and revalidates on every update, revert, read and press. The browser renders only catalog components with `textContent`/DOM APIs under the existing CSP (`script-src 'self'`, no inline script/style), so spec text, HA names/states and household notes cannot inject markup or script; unknown or malformed blocks render as an “Unsupported block”. Every displayed value is a controller read with its observation time; a spec can never supply a value, URL, style or callback. Model tools can create/update/read apps but have no path to press controls, tick checklists or edit household data, and they exist only in Home conversations (never Code). ToggleAction presses are authenticated, Origin/CSRF-checked owner requests that pick the service from a fresh state read and then enter the same Home permissions broker and action ledger as model proposals: Read-only denies before any HA request, Ask files an exact proposal for human approval, Full dispatches once within the current owner/revision/policy-bound grant; unknown outcomes are never retried and pause writes to the same entities until they are settled. AskButton drafts text only. App reads are rate-limited and bounded (24 scope entities, 2 charts × 3 entities × 48 h, 2 MB HA responses, 48 points). Apps are owner-scoped like sessions; deletion retires documents but does not securely erase committed history. Checklist items and notes typed by household members are untrusted if later shown to a model.

Household memory and suggestions (unreleased, L1/L2): memory items are owner-entered or owner-accepted plain text (one line, ≤200 characters, credential-redacted), stored per owner in a Pi Durable document written only by that owner's authenticated, Origin/CSRF-checked requests. They reach Home prompts in a separate `household_memory` section marked OWNER-APPROVED CONTEXT that states it never grants permissions, widens scope or overrides safety rules; angle/square brackets are replaced and line breaks removed so item text cannot close the section tag or forge its BEGIN/END markers, and at most 4 KB is included (oldest trimmed first). This is a prompt-level boundary, not a guarantee against injection: memory text is treated as untrusted data like any other content, and every permission is still enforced by the controller (Home permissions broker, exact scopes), never by prompt text. Forget removes an item from the document and later prompts but is not a secure erase (committed document history and earlier prompt entries in existing transcripts remain in `/data`). Model tools `suggest_memory` and `suggest_app_change` exist only in Home conversations and only create proposals; the proposal schema has exactly two kinds (`memory`, `app_change`), with no field or kind that can touch Home permissions, entity/service scope, credentials, providers or settings (unit-tested), and app patches pass the same full HAS/1 validation as `app_update` at proposal and acceptance time. Acceptance is an owner UI request bound to the proposal hash and recorded with the owner's ID; an app change applies only at its base version (otherwise a recorded conflict). Rejections suppress the same normalized text or patch hash for 60 days; proposals are rate-limited per conversation and per owner per day. After a 👎 with reasons in an app-building conversation, the next owner turn gets an `owner_feedback` section with message ids and reason enums only; nothing runs in the background.
Code-level improvement suggestions, L3 (unreleased): the only new signal is a bounded, durable, per-owner counter of Home tool failures (`hearth.tool-failures`: tool name, error code, timestamp; 7-day rolling window, pruned on every write) built purely from the Harness's own tool results \u2014 either a thrown Fault's exact `code` or a tool's own structured `{..., error: "code"}`, both already surfaced to the model today, never prompt or response text. Counting wraps every Home tool uniformly at the extension boundary (`withFailureSignal`); a counting failure is swallowed, never altering or blocking the tool's own result, and nothing is counted for a Code (workspace) session. A new `tool_health` prompt section tells the model, in counts and error codes only, which (tool, errorCode) pairs have reached 5 in the window; that is the only way the model learns to call the new Home-only tool `suggest_code_change(title, problem, proposal, evidence)`. The tool re-validates the claimed evidence against the real counter inside the same request (refusing a claimed count above what was actually recorded, a pair that never reached the threshold, a non-exact tool/errorCode shape, or title/problem/proposal text containing a code fence, a unified-diff header or an import/function/class-shaped line) before filing a `code` suggestion kind in the existing Today inbox; filing never changes anything, exactly like `suggest_memory`/`suggest_app_change`, and the schema still has no field or kind that can touch Home permissions, entity/service scope, credentials, providers or settings. A `code` suggestion whose title/problem/proposal mentions a security-sensitive keyword (scope, approval, permission, credential, token, sandbox, CSP, sanitizer, risk, judge, supervisor) is marked `securitySensitive` and the UI gates its action behind opened details plus a typed confirmation (`CONFIRM`); the server independently re-checks that confirmation (`confirmation_required` on mismatch) before doing anything \u2014 the client-side gating is a UX aid, not the enforcement boundary. A `code` suggestion's only action besides the existing Reject/Snooze is **Draft in Code session** (`SuggestionStore.draft`), which calls the existing, unmodified session-creation path (`Runtime.create(..., "workspace")`, refused with `workspace_not_enabled` exactly as `/api/sessions` already refuses it when Code sessions are off) and then `Runtime.submit`s one fixed template message into that brand-new session: the suggestion's problem/proposal/evidence, explicitly labelled as untrusted owner-reviewed data the worker must treat as data and never as an instruction, plus an instruction to produce a patch, a unit test and a short PATCH SUMMARY. This is the same offline, non-root, confined worker used by every Code session (see [workspace.md](workspace.md)): no Home Assistant tool, no network and no provider/HA credential reaches it, and nothing here changes that confinement. **Hearth never applies the result to itself**: there is no tool, route or code path that writes the worker's output back into the running installation (a static test asserts `draft()`'s only effects are `runtime.create`/`runtime.submit`, and that `suggestions.ts` has no filesystem or process-execution import); the owner reviews the patch inside that ordinary Code session and releases it through their own normal commit/CI/Supervisor-update flow, like any other change to this repository.

Automation troubleshooting (unreleased, read-only): Home conversations get four read tools for automation entities that are themselves in the exact configured read scope. Config is read with REST `GET /api/config/automation/config/<id>` (HA also serves POST/DELETE on that path; Hearth's reader is constructed with a GET-only function and a static test rejects write verbs, `fetch` and service paths in the new code). Traces need HA's WebSocket API: a minimal client connects to `ws://supervisor/core/websocket`, authenticates with the Supervisor token and can send only `auth`, `trace/list`, `trace/get` and the three read-only registry lists used by Home World (`config/area_registry/list`, `config/device_registry/list`, `config/entity_registry/list`) through one allowlisted send function; registry create/update/delete, floor/label registries and all other types (e.g. `call_service`, `execute_script`, `subscribe_events`) are refused before a frame is written. Sessions are short-lived, with a 10 s deadline, 1 MB per frame, 4 MB per session and 8 commands; frame text is redacted before parsing. Both endpoints require HA admin; the broad Supervisor token is not narrowed by this feature, so policy is enforced by Hearth's fixed tools. Residual risks: (1) trace and config text are untrusted and could carry prompt injection — they are returned as data, scrubbed and size-bounded, and the model has no tool that can change configuration; (2) traces capture values of any entity the automation touched — trigger states are shown only for in-scope entities, other entities referenced by the config are named as outside the read scope and not read, and condition observations/rendered action data are withheld whenever any reference is outside scope, a device ID or an indirect template, but detection of references is pattern-based; (3) secrets resolved into configs/traces (from `!secret` or literal values) are only removed by configured-secret redaction plus key/URL/bearer/JWT patterns, so an unusual secret format may survive — keep such automations out of `allowed_entities` if in doubt; (4) drafted YAML is model output the owner must review before pasting; Hearth cannot apply it.

Home World (unreleased): the house is generated by the controller from the area, device and entity registries, read over the same allowlisted WebSocket client (only the three `…/list` types; registry sessions allow 3 commands, 8 MB per frame, 16 MB total and a 10 s deadline, cached for 5 minutes). The registries are broad, so the reply is projected immediately to the entities in `allowed_entities`: only their area id/name/floor id and device display name are kept; other entities, config entries, unique ids, pictures, aliases and labels are discarded before anything reaches the browser or a model (tests assert this). Names are redacted and length-bounded and rendered with `textContent` only. Device values are the existing scoped state reads, rate-limited per owner. World toggles accept only drawn light/switch entities with both on/off services configured, choose the service from a fresh read and enter the same Home permissions broker and action ledger as app ToggleActions (origin `world`): Read-only denies before any HA request, Ask files an exact proposal for human approval, Full access dispatches once within the owner's grant; unknown outcomes block writes and are never retried. Think-mode motion is derived only from the durable `pi.live` tool round and a call's `entityId` argument; the world modules make no requests of their own (app.js passes request helpers) and use no `innerHTML`/`eval` (static test). Owner customization is a strictly validated Pi Durable document (bounded rooms/devices, no unknown keys, in-scope entities only) with optimistic concurrency; like other documents it is not securely erased on reset. The one-time prototype import accepts only the old schema and never repairs invalid input.

Admin access mode (unreleased, owner opt-in via `access_mode: admin` in the App configuration only): Hearth reads every entity, registry and automation/script/scene config and allowlisted Supervisor information, and can propose any service call, config write/delete, allowlisted registry/helper WebSocket mutation and allowlisted Supervisor action. Threats and controls: (1) **prompt injection** through entity names, attributes, automation/trace text, add-on names or logs can steer the conversation model into proposing harmful changes — every mutation is an exact durable proposal classified by deterministic controller rules (`src/risk.ts`) that never read model or tool text and fail closed: whenever the classifier cannot see what an action would do it rates it high, never lower — every automation/script write is at least high (a stored automation can later act without a person) and critical when its serialized body mentions a critical service in any form (templates, any letter case, beyond any item count); scenes are rated by their member domains (`scene.turn_on` by the live `entity_id` attribute of the target scene), covers by one live read of every target (missing, unreadable, door/garage/gate, or device/area targets → high), `update.*` on Core/OS/Supervisor or unverifiable update targets → critical, renaming/hiding a cover/lock/alarm/siren/camera → high, and self-protection applies to every domain's targets (Hearth's slug, Supervisor-reported name, entities); Full access auto-runs only low risk (medium only with an agreeing judge), high and critical always need exact human approval (the one exception is the owner opt-in for trusted people below), and Ask/Read-only behave as before; (2) the **risk judge** is a separate tool-less call that sees only the owner's latest message, the exact action JSON and the deterministic level, plus at most the last 4 prior exchanges (earlier owner requests, earlier exact actions, its own verdicts) of an in-memory per-owner/per-conversation/per-model session (TTL default 5 minutes, never durable); it never sees tool output, entity attributes, logs, memory or secrets (canary-tested), it can only escalate or flag a mismatch, and any error, timeout or garbage fails closed to Ask — a compromised judge can make Hearth ask more, never less; (3) **critical confirmations** (host power, backup restore/remove, add-on uninstall, system updates, self-targeting) require a typed word in addition to approval, checked server-side; (4) **self-protection**: actions that stop, reconfigure, update or uninstall Hearth's own add-on, or configs referring to it, are critical; (5) Supervisor access goes directly to Supervisor's own REST API (`http://supervisor/<path>`, `Authorization: Bearer $SUPERVISOR_TOKEN`) rather than through Home Assistant Core: Core's `supervisor/api` WebSocket command rejects the add-on's Supervisor-proxied connection with `{"code":"unauthorized"}` because it is not an HA admin user (verified against a real Home Assistant 2026.9 / current Supervisor install). The manifest grants the add-on's token Supervisor's **manager** role (`hassio_api: true`, `hassio_role: manager`) in **every installation**, not just admin-mode ones; **manager is broad** — Supervisor's own role table (`api/middleware/security.py`) gives it every endpoint Hearth allowlists below and nearly everything else except an add-on's own protection-mode toggle, OS datadisk wipe and host SSH authorized-keys, so **Hearth's fixed, re-checked-before-every-send path allowlists and safe-field projections are the actual enforcement boundary, not the token's role**; a compromise of the controller process could use the full manager role, including endpoints Hearth itself never calls. Hearth never requests `hassio_role: admin`. Scoped mode never registers or calls a Supervisor tool regardless of the token's role — enforced in code (`src/ha.ts`), checked before any network call. Mutations distinguish a definite pre-handler 4xx (token/role/shape rejected, nothing happened: reported **failed**, not retried) from a network error, timeout or 5xx after the request may have reached Supervisor's handler (reported **unknown**, pausing every Home write until a human reconciles it — Supervisor actions can reach anything — never retried either way); no redirect is ever followed, responses are size-capped, and backup create/restore and add-on install/update ask Supervisor to queue a background job instead of holding the request open. Still no host shell, filesystem or Docker; (6) Supervisor info reaches the model only through per-endpoint safe-field allowlists (never add-on options/schema, network maps, ingress entry URLs or backup protection details), admin entity attributes are bounded (≤40 keys, ≤200 characters, secret-like keys, nested objects and tokenized picture URLs dropped), and logs and config text are redacted (configured secrets plus bearer/JWT/`sk-`/password-shaped values) and capped, which is not detection of every secret format; (7) an optional `endpoint/` judge server receives the owner's request and action JSON, must be on a private address (re-checked each call, no redirects) and its key is redacted like other secrets. Unknown outcomes of every action kind pause writes (every write for configuration, registry, Supervisor and other house-wide actions; the same entities for entity service calls) until settled and are never retried. Admin mode trades least privilege for convenience; prefer Ask.

Admin mode residual risks (inherent limits of rule-based classification): the classifier rates by domain, service, targets and live attributes, not by what a device physically does. A `switch.*` (or `light.*`) entity that actually drives a lock, gate or garage relay, with an innocuous name and no opening device class, is rated low like any comfort switch and can auto-run under Full access. Owners who have such relays should give them a revealing name or device class, keep Home permissions on Ask, or stay in Scoped mode. `automation.turn_on/off` and other medium-rated service calls on existing automations rely on the automation body having been gated at high or critical when it was written; automations created outside Hearth were never classified by it. The judge is a second opinion only: it can escalate or flag a mismatch, never approve, and a misjudgment can at most leave a medium action that the deterministic rules allowed.
Image attachments and Home World setup (unreleased): owners can attach up to 4 images to a Home chat message (for example a floor-plan photo). The browser re-encodes each to JPEG of at most 2048 px; the server does not trust that: it decodes strict base64, identifies the type by magic bytes (JPEG, PNG and WebP only; HEIC/HEIF/AVIF, SVG, GIF and anything else are refused, and a declared type that disagrees with the bytes is refused), and bounds each image to 4 MB and 4096 px per side, a message to 10 MB and a conversation's active transcript to 12 images. The inputs request body may be up to 14 MB and the server's request timeout is 60 s (other bodies keep their 8–32 KB limits and 5 s read deadline). Images are stored inside the durable Pi user message (Pi Durable's `UserInput` carries pi-ai `ImageContent`); the controller's inputs document holds them only until the message is placed. Session snapshots and SSE carry only a reference; bytes are served by `GET /api/sessions/<id>/images/<entry>/<n>`, which is authenticated, owner-checked through the session like every session route, re-identifies the bytes, sets the image type explicitly with `nosniff`, and is privately cacheable. CSP allows images from `'self'` and `blob:` (for the composer's local thumbnails) only. Images go to the session's model provider as part of the conversation context on every request in that chat, and nowhere else. A session whose model does not accept image input refuses the message (409 `model_no_image_input`) instead of silently dropping the image. Images are untrusted input: text inside an image is data, never instructions, and the system prompt says so — this is a prompt-level statement, not a guarantee against injection; every permission is still enforced by the controller. Like transcripts, images are not securely erased by deleting a session.

Bundled skills (`hearth_pi/skills/<name>/SKILL.md`) are repository content, reviewed like code, packaged read-only into the image and loaded once at startup with strict frontmatter and a 24 KB limit. Home prompts list only their names and descriptions; `hearth_skill` returns one skill's text by looking the name up in that fixed set (a strict name pattern; no path is ever built from model input), and no tool can write or add a skill. The Home World setup tools read the same scoped registry projection as the Home World routes (`world_layout_get`, bounded output) and `world_layout_propose` only stores a validated per-owner draft (one per owner, 7-day expiry) in the Home World layouts document without touching the saved layout or its revision. Keeping a draft is an authenticated, Origin/CSRF-checked owner request with the draft id and the saved layout's revision, revalidated exactly like an editor save; Discard is the same kind of request. No tool changes Home Assistant areas, floors, devices or any configuration.

Undo (unreleased): right before a low/medium proposal is dispatched, the controller makes one bounded (2 s) read of the single entity an allowlisted action changes and commits a ≤1 KB snapshot (state, last change and allowlisted numeric/boolean attributes only — no names) with the dispatch intent, before the POST; a failed read only means no Undo. Undo is an allowlist of single-entity reversible actions (no device/area/multi-entity targets, no config/registry/Supervisor actions, no list removals), refused for high/critical (final, judge-escalated level), failed/unknown/resolved outcomes and for reverse proposals themselves. It never dispatches directly: the reverse is a new exact proposal (`origin: undo`) through the same admission as a person's press — Read-only, Ask, Full grant, the unknown-outcome barrier, live validation and the deterministic classifier — and it is forced to ask when the entity changed again more than 30 s after the original attempt. Single use is recorded in the same commit that creates the reverse proposal. Undo restores a pre-change reading; it cannot prove that reading still reflects intent, and the reverse can itself have an unknown outcome.

Phone approvals (unreleased, App option `approval_notifications`, default off, ingress only): a second, narrow way to decide a pending proposal besides an authenticated Ingress request. Controls: (1) **binding** — the only accepted input is a Home Assistant `mobile_app_notification_action` bus event whose `context.user_id` equals the proposal's owner, whose `origin` is `REMOTE`, and whose action id is `HEARTH_A_`/`HEARTH_R_`/`HEARTH_P_` plus 128 random bits (upper-case base32) that Hearth issued for one proposal id and hash (or one phone proof) and keeps only in memory, single-use (a tap burns its sibling too), until the proposal expires; a missing or different user id fails closed. Action ids are visible on the HA event bus and recorder to HA admins, so the nonce is linkage and replay protection, not the authentication; HA's user attribution is. (2) **scope** — approve only for low and medium; high and critical notifications carry no approve token and `HomeActions.decide` refuses a phone approval above medium (`push_approval_not_allowed`), so they always need the exact card (critical also its typed word). No free text (`reply_text`) is read. Every decision then goes through the same `decide()` checks as the UI: hash, pending, Home permissions and revision, expiry, policy and the unknown-outcome pause. (3) **enrollment** — candidate phones come only from controller reads (the owner's `person` entity → its `device_trackers` → entity registry entries of platform `mobile_app` → device registry → an existing `notify.mobile_app_<device>` service). HA does not expose who registered a device, so a phone is used only after a round-trip proof: a notification with an "It's my phone" action tapped by the owner's own HA user within 10 minutes. Phones are re-checked against the owner's candidates at every send and disabled when they no longer match; a device tracker re-registered under the same name to another person is limited, not excluded, by this. (4) **sending** — a fixed controller-only notifier (`HAClient.notifyDevice`) posts one fixed-shape payload to `notify.mobile_app_*`; it is in no extension, tool or proposal path, and scoped `allowed_services` still never admits `notify`. The text is the risk level and a deterministic one-line headline (service and entity ids, config resource and id, or Supervisor method and path) — never `data`/`body` values, friendly names or list item text — redacted and capped at 100 characters. `Proposal.notified` is committed before the send, so a proposal is sent at most once and a failed send is never retried; at most 20 sends per owner per hour and 5 phone proofs per hour. (5) **listening** — a separate long-lived WebSocket (`src/ha-events.ts`) whose only frames are `auth`, one `subscribe_events` for `mobile_app_notification_action` and `ping`; frames over 64 KB drop the connection; reconnects back off 1–60 s; event processing is capped at 30 per minute. Residual risks: `authenticationRequired` on the Approve button is honoured by the iOS Companion app; Android may allow a lock-screen approve without unlocking, so anyone holding an owner's unlocked-notification phone can approve a low/medium action. A medium action's one-line headline can be opaque (for example a button press). Taps made while disconnected are lost. Verified against fakes only: the live event's `context.user_id`/`origin`, action-id case preservation and the `/hassio/ingress/<slug>` link must be checked on a real installation before relying on it.

Trusted people (unreleased, App option `trusted_user_ids`, default empty, owner opt-in): with the default nothing below applies and Home permissions behave exactly as described above. Each listed ID must be an authorized owner (startup refuses members, guests and unknown IDs: `trusted_user_not_authorized`, `trusted_user_not_owner_role`, `invalid_trusted_user_ids`; the engine re-checks at attach time). For a trusted person on **Full access**, a proposal from their own direct turn auto-runs at **every** risk level — low, medium, high and critical — without the risk judge (it is not called) and without the typed confirmation word; the receipt records `authorization.source: "trusted"`, the deterministic level and rule. A direct turn is an input the server marks `direct` in the same commit that admits it: text typed in the authenticated Hearth UI, or the Assist button under the person's own Home Assistant user. Satellite inputs carry the Ask ceiling and can never be direct (`Runtime.submit` refuses the combination), so a run with any satellite input stays Ask; a run with any input without the mark (anything Hearth or another system submits for the person) follows the normal Full rules (low only, medium with an agreeing judge, high/critical ask). The person's own presses of app, Home World and list controls run on Full too, except Undo's forced ask. Trusted widens approval, never the policy: the action still passes the same exact-scope validation (Scoped: configured entities/services only; Admin: no host shell/filesystem/Docker), Code stays separately confined, every input of the run must still be bound to the current Full grant (no upgrade of earlier inputs), the automatic dispatch re-checks trust, the ceiling, the direct mark, the grant and the input set inside the dispatch commit, and unknown outcomes are never retried. The trusted Full acknowledgement text states that every risk level runs without asking; switching to Full still needs that one explicit confirmation, and adding or removing someone from the list invalidates their earlier Full grant (the acknowledgement no longer matches). Residual risks: model mistakes and injected content (entity names/attributes, automation and trace text, images, memory) can now run high and critical actions — unlocking, opening garages/gates, disarming alarms, restarting or updating Home Assistant, rebooting the host, restoring/deleting backups, changing Hearth itself — for a trusted person without a second look; the risk classifier still labels each receipt but no longer stops anything for them; anyone who can type in a trusted person's signed-in Hearth session or press their Assist button acts with this power. What remains: the exact policy bounds, Read-only/Ask on demand, Emergency Read-only, the satellite ceiling, per-entity pause and no retry of unknown outcomes, durable receipts with level and rule, and the guarantee that the list is set only in the App configuration, never by the UI, a model or a suggestion. Residual risk: Home Assistant's conversation input does not distinguish the Assist button from a user-initiated script or dashboard action that calls `conversation.process` with Hearth as the agent; both carry the person's user context and therefore count as their direct turn. In admin mode an injected proposal could write such a script that a trusted person later runs; owners should not let others edit scripts that call Hearth.

Injection guard (0.7.0, App options `injection_guard_url`, `injection_guard_api_key`, `injection_guard_timeout_ms`; off while the URL is empty): one wrapper at the Home extension boundary (`withInjectionGuard`, outermost around every Home tool of every role group, `src/ha.ts`) sends each Home tool result's text blocks to an owner-run classifier (`POST <url>/v1/guard/injection`, contract in DOCS.md) before the result reaches the model. Controls: (1) **flagged** output is never removed or rewritten; a fixed untrusted-data warning is prepended and, before the result is returned, a marker (`guard: {result, score, tool, at}`, never content) is committed on every input of the conversation's current run; if that commit fails the tool fails rather than hand flagged text to an unmarked run. (2) A model proposal's effective mode is the lower of the owner's mode and the run's marks, so in a marked run Full falls to a pending Ask proposal for exact human approval — also for trusted people, whose trusted path also refuses a marked run — and the receipt records `authorization.guard: "flagged"` (shown as "Ask: outside content looked like instructions"); automatic dispatch re-checks the mark inside the dispatch commit (`input_guard_flagged`). Follow-ups the person typed while the marked run was still working (queued in the conversation's inbox, admitted but not yet queued, or admitted later in the same run) carry the mark too, fail safe. Inputs of later runs carry no mark, so the taint is per turn by design: the owner's next turn auto-runs again as before even though the flagged text may still be in the conversation context. Nothing else is weakened: no upgrade of earlier inputs, satellite ceilings, roles, exact policy, the unknown-outcome pause and no-retry all apply unchanged; a person's own control presses are not model turns and are unaffected. (3) **Fail open for chat, not for safety decisions**: when the guard is unreachable, slow (`injection_guard_timeout_ms`), refuses the key, answers `scanned: false` or malformed JSON, the result passes **unscanned and unmarked** and only a counter and an error class are kept (Settings → About: "Injection guard: unavailable"); unscanned is not the same as safe, so the controls that never depended on the guard (deterministic risk classes, Ask, judge, high/critical approval for untrusted Full) remain the real boundary. (4) The guard sees tool output (entity names/attributes, automation/trace text, logs, list items, app specs — whatever the Home tools already return to the model), so it must be a service you trust with that data: the URL must resolve to a private/loopback address (re-checked per call, `supervisor` host refused, no redirects, bounded 64 KB reply), the key is in the redaction list and is never logged, returned by `/api/injection-guard` or shown, and log lines carry only counters and error classes. Residual risks: classifiers have false negatives (paraphrased, encoded, split or image-borne instructions) and false positives; text past 32 pieces / 400,000 characters per result is not scanned; tool errors (`Fault` codes) and Code-session tool output are not scanned; user messages, attached images, memory and profile sections are not tool results and are not scanned; content flagged in one turn stays in the conversation and can still influence a later turn, whose proposals then follow the normal rules; parallel tool calls in the same model step can be decided before a flagged result of that step is marked (the proposal was chosen without seeing it). Verified against a fake guard service and the offline durable harness only.

Unknown-outcome reconciliation (unreleased): after a dispatch ends unknown (or a restart turns an interrupted one unknown), the controller reads the target entities back from Home Assistant about 5 s, 30 s and 2 min later, through the same scoped state reads Undo uses (or the list read for shared lists). It never sends a service call. If every target reports the requested state, the receipt becomes resolved with **Succeeded (confirmed from Home Assistant state)**; if at the last check every target still matches the reading taken right before the attempt — same state, same allowlisted attributes and the same `last_changed`/`last_updated` — it becomes **Did not happen (confirmed from Home Assistant state)**; otherwise it stays unknown for a person. Each check is a receipt note. Only actions with a well-defined target state reconcile (an allowlist: light/switch/`input_boolean`/fan on/off, light brightness, toggles from a known on/off reading, cover open/close, lock/unlock, climate temperature or HVAC mode, `input_select` option, list add/complete/reopen/rename/remove); configuration, registry, Supervisor, scenes, scripts and device/area targets never do. Residual risks: Home Assistant state is what the integration reports, not physical truth; a target that reached the requested state some other way (another person, an automation) also counts as succeeded; list checks have no timestamps, so a list item changed and changed back within two minutes could read as "did not happen"; some battery radio devices run a queued command only when they next wake up, possibly after the last check, so "did not happen" can be overtaken by a late effect (toggles are therefore never marked "did not happen", since a late toggle plus a new one would cancel out); a person who then asks again sends a new, separately admitted action.

Follow-ups while a turn runs (unreleased): a message the signed-in person types in a Home chat while Hearth works is admitted like any composer input (own `Inputs` record with the `direct` mark and the permission binding of that moment, same idempotency key rules) and queued as a Pi Durable follow-up (`whenBusy: "followUp"`), which Pi Durable places only when the run answers and which then starts a run of its own; it never joins the running run, so it cannot inherit that run's approvals or authorizations and the existing checks (no upgrade of earlier inputs, trusted direct-turn rules, satellite ceilings, roles, the unknown-outcome pause) apply to it unchanged. Only the composer route requests this (`followUp`, set by the server, never from a request body, and only together with `direct` and no channel); Hearth Assist, Code suggestions and Code sessions keep refusing a busy chat (`session_busy`), Code because its uncertain-operation pause counts human inputs. At most 3 follow-ups wait per chat. Model changes stay refused while a run or a queued follow-up exists. Stop withdraws queued follow-ups (they settle unanswered). When a run fails, Pi Durable leaves its queued follow-ups in the inbox with nothing running until the next submission places them, oldest first; the browser keeps Stop shown and enabled while any wait (and says so instead of "sends when Hearth finishes"), and `/abort` on such an idle chat withdraws them (tested). Residual risk: a follow-up is bound to the Home permission (mode, revision, policy, Full grant) of the moment it was typed; if that permission changes while it waits and is Full when it runs — a window that queueing makes longer than a single run — its automatic dispatch fails closed with the tool error `input_permission_not_elevated` rather than falling back to an Ask card, so the person must send the request again. Nothing runs without the matching grant. In the browser, an unsent message is discarded only after a definite refusal (a 4xx with a known code that the server returns before admitting anything); after a network error, timeout or 5xx only Retry with the same request ID is offered, and the refusal mark is cleared before every attempt.

Device and integration setup (unreleased, Admin access mode only; `src/flow-setup.ts`): Hearth can propose Home Assistant config flow steps — start (`POST /api/config/config_entries/flow` with `{handler}`), submit values to the current step (`POST /api/config/config_entries/flow/<flow_id>`) and cancel (`DELETE` on that path) — as a new `flow` action kind through the same Home permissions broker, classifier and ledger, and reads discovered flows (`config_entries/flow/progress`, which lists every flow not started by a user: discoveries, but also `reauth`, `reconfigure`, `import` and `system` flows, which are listed with their source but never stepped or cancelled by Hearth: `flow_source_not_supported`, also when the source changes before dispatch, and also for a flow without a reported source), the handler list (`GET /api/config/config_entries/flow_handlers`) and config entries (`config_entries/get`). The two WebSocket types are added to the admin socket's allowlist only, never to the scoped read client. Controls: (1) **validation** — handler `^[a-z0-9][a-z0-9_]{0,63}$`, flow id `^[A-Za-z0-9]{8,64}$`, `user_input` flat scalars only (string ≤256 characters without control characters, finite number, boolean, null), ≤20 keys, ≤4 KB, no `__proto__`-style keys, no entry id (reconfigure), options or subentry flows; (2) **flow identity** — a step or cancel takes its handler and current step from Home Assistant's discovered list or from Hearth's own accepted receipts for a flow it started in the same conversation (the flow id adopted from Home Assistant's reply to that start), never from the model; a mismatch or a flow neither knows is refused, and a discovered flow Home Assistant no longer lists stays `flow_not_found` even when Hearth's receipts show an earlier step on it; right before the request, a discovered flow is re-read from Home Assistant and a flow Hearth started is re-checked against its receipts inside the dispatch commit (`flow_changed` if it moved on to another step, ended, or another action on the same flow is being sent), so a stale pending step is never sent to whatever step is current; (3) **risk** — every flow action is high (`integration_setup`, `integration_setup_step`, `integration_setup_abort`), so it asks on Full access for everyone except a trusted owner's own direct turn; it is critical with the handler as the typed word for Hearth's own handler (`hearth_pi`, or values that mention Hearth) and for a fixed list of integrations that let something outside the home reach or control it (`cloud`, `homekit`, `mcp_server`, `remote_homeassistant`); a guard-flagged turn always asks; (4) **secrets** — `user_input` keys matching `pass|token|key|pin|code|secret|pair|psk|otp|credential|cert` (any case), fields Home Assistant itself returned as password selectors on the step the flow is at (from Hearth's own receipt for the previous step, for flows Hearth started and discovered ones alike; the first step of a discovered flow has no schema in Home Assistant's list, so only the name and value-shape checks apply there), values shaped like bearer/JWT/`sk-`/PEM credentials and values containing a configured secret are refused before a proposal exists (fault codes only, never the value), so they never reach a proposal, card, receipt, phone headline (handler, op and step id only) or log; the model is told to send the owner to Home Assistant's own UI (fixed paths `/config/integrations/dashboard`, `/config/integrations/dashboard/add?domain=<handler>`, `/config/integrations/integration/<handler>`, rendered as a link only when they match that pattern); (5) **receipts** — Home Assistant's reply is read with a 256 KB cap, redacted and reduced to type, flow id, handler, step id, ≤30 field names/types/required flags (≤20 option values for selects, never for secret fields), ≤20 menu options, ≤20 error codes, an abort reason and, on create, the entry id and a ≤100-character redacted title; field values, defaults, descriptions, description placeholders (which can carry codes), external-step URLs and entry data are never kept; (6) **outcomes** — HTTP 400 with per-field `errors` (schema validation before the step handler), 401/403/404/405 and redirects are **failed** (nothing happened); a network error, timeout (60 s), 5xx or other status is **unknown**, pauses every Home write (no entity scope) and is never retried; there is no automatic reconciliation, because Home Assistant exposes no read-only view of a user-started flow, so a person resolves it after checking Settings › Devices & services. Residual risks: an integration's own code runs inside Home Assistant once a step is approved (it may contact the device or a cloud service, install requirements or create entities that later act); a name-based secret check cannot catch a secret the owner types into an innocently named field, or into chat — the model's own call arguments for a refused proposal remain in its transcript; field names, option values, error codes and titles come from the integration and are untrusted text (bounded, redacted, rendered with `textContent`); the remote-access list is short and explicit, so another integration that exposes the home (a tunnel, a voice-assistant bridge, a backup uploader) is rated high, not critical; and the flows Hearth starts but does not finish stay in Home Assistant's memory until cancelled or Home Assistant restarts. Verified against a fake Home Assistant flow API only.

## Local risk judge

The risk judge described above (point 2) is optional and, by design, can only **escalate** a deterministic risk level or flag a mismatch — never lower a level, never approve a mutation, never act. The experimental **Hearth Judge** add-on (`hearth_judge/`) is one way to run it: a small open-weight model served by the official `ghcr.io/ggml-org/llama.cpp` server, on the same Home Assistant host, reachable only on the internal `hassio` network (no `ports:`, no ingress, no `homeassistant_api`/`hassio_api`). Choosing it (`risk_judge_model: endpoint/<model>`, `risk_judge_url` pointed at the add-on) keeps the owner's latest message and the exact proposed action JSON on the host for judging, instead of sending them to a cloud provider; the conversation model itself still sees them, as always, and classification itself is still the deterministic floor (`src/risk.ts`), never the judge. Hearth Judge never reads Home Assistant state, never gets a Supervisor or HA token, and its optional `api_key` only protects that one endpoint. Its model is downloaded once and sha256-verified against a pin recorded in `hearth_judge/models.json`; `run.sh` refuses to start if that pin is missing or malformed. A tiny local model is expected to be a weaker judge than a cloud one — run [the evaluation harness](../hearth_pi/eval/) (false-agree rate and escalation recall especially) before relying on it for anything beyond low-risk actions, and keep `risk_judge_timeout_ms` above its measured p95 latency so a slow reply fails closed to Ask instead of silently "no agreement". See [hearth_judge/DOCS.md](../hearth_judge/DOCS.md) for its own threat notes (non-root process, writable surface limited to `/data`, no declarative read-only-rootfs option in this add-on's manifest).

Hearth Assist (App option `assist_enabled`, default off, ingress only): Home Assistant Core's conversation agent (the `hearth_pi` custom integration, installed by the user through HACS; the App never writes Core's `/config`) reaches Hearth on a **separate listener** (port 8098 inside the Supervisor network, never published on the host), because Core calls from host networking and the Ingress boundary must keep trusting only the Supervisor proxy peer. Controls: (1) **authentication** — `Authorization: Bearer <link secret>`, a 32-byte random value in `/data/core-link.key` (`0600`), compared in constant time over SHA-256 digests; any request carrying an `Origin` header is refused (`403`), there are no cookies or CSRF tokens, bodies are strict JSON capped at 8 KB, headers at 8 KB, connections at 20. (2) **hand-over** — the secret reaches Core only through Supervisor discovery (`discovery: [hearth_pi]`; only Core can read discovery messages; an add-on can publish only service names listed in its own manifest), the way other add-ons hand Core broker credentials. It then lives in Hearth's `/data`, Supervisor's discovery store and Core's config entry, hence in backups. It is redacted from every response, log line and transcript; never shown in the browser, Settings or diagnostics. Owners can rotate it (Settings → About; Origin/CSRF-checked, explicit confirmation); the old value stops working at once and the new one is published again. (3) **identity** — the link secret proves the caller is Core, not who is speaking. Hearth resolves the person itself: a turn from a satellite (a `satellite_id`, or a device in the map) always uses the admin-set `assist_satellites` device map with the Ask ceiling, even when Core attaches a user context, and an unmapped satellite is refused; otherwise an authorized `context.user_id` (the Assist button) is that person with their normal permissions and household role; the device map (App configuration only, every user validated against `authorized_user_ids`) names the person, with an **Ask ceiling**; anything else (unknown users, unmapped satellites, no user, automation-started turns with an extra system prompt) is refused before any chat or model call. Anyone holding the secret, or a Core compromise, can therefore speak as any authorized person — satellites only through the Ask ceiling — which is why the secret is treated like the Supervisor token. (4) **ceiling** — inputs record their channel and ceiling in the same commit that admits them. A model proposal's effective mode is the lower of the owner's mode and the run's ceiling, so Full falls to a pending Ask proposal for exact human approval instead of failing; automatic dispatch re-checks that no ceiled input is in the run (`input_channel_ceiling`). The existing checks are unchanged: inputs admitted under a weaker permission still cannot be upgraded later. Voice can never approve: there is no approval tool, and a spoken "yes" is ordinary chat text. (5) **turns** — one rolling Voice chat per person, a durable map of recent request ids (`assist-<context.id>`) to chats so a repeated request is never run twice or in a second chat, per-person and refused-request rate limits, and at most 4 voice turns at once; the turn is never cancelled when the connection drops. (6) **speech** — the closing sentence is written by the controller from committed proposals and receipts, and claims a phone push only when Home Assistant accepted that notification for at least one confirmed phone. Residual risks: speech-to-text mistakes reach the model and the optional risk judge as if they were the person's words; Home Assistant's own **Prefer handling commands locally** runs the commands it recognizes without Hearth (none of Hearth's permissions apply), so sensitive devices must not be exposed to Assist; transcripts also land in Home Assistant's Assist debug view and conversation history; Core's conversation API may change. Verified against fakes and `pytest-homeassistant-custom-component` only, not yet on a live installation.
