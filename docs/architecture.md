# Architecture (0.2.0)

Browser → authenticated Node controller → genuine Pi Durable 1.0.1 harness/SQLite store. The fixed HA REST client and model runtime are separate capabilities. The Docker context is `hearth_pi/`. Supervisor supplies options and the HA token; root bootstrap restricts known data files and initializes the optional private IPC bridge, then drops permanently to UID/GID1000 before model/harness/network work.

`Runtime.open` verifies exclusive SQLite WAL ownership and `synchronous=FULL`, initializes documents, invalidates pending approvals, marks dispatching actions unknown, binds stored conversation kinds to explicit extension groups, drains input reservations and resumes tasks. Catalogue binds session IDs to operators; input IDs bind to hashes. Reservation and harness submission are separate commits, drained idempotently at restart. HTTP202 follows durable admission. SSE sends full authoritative snapshots; reconnect hydrates state. Four active conversations, bounded histories/streams/output and eight model rounds constrain resource use. Model requests/safe HA reads can repeat after recovery and consume account allowance/cost.

## Capability groups

**Home:** `ha_search_states`, `ha_state_detail`, `ha_discover_services`, `ha_propose_service`, plus the **unreleased branch** `ha_build_view`. No arbitrary shell/filesystem/admin/API tool. The broad HA token is narrowed by fixed routes/output scope. Up to10,000exact IDs are configured, with bounded twenty-item search pagination and count-only bootstrap diagnostics; no wildcard/all-future grant. Proposals bind immutable action/session/task/hash, policy and five-minute expiry. A shared `HomeActions` engine is attached before recovery/resume and owns both manual and automatic dispatch. Home permissions are owner-keyed in a session-scoped Pi Durable document, not another database: Read-only when actions are disabled, otherwise Ask by default. Explicit Full acknowledgement is bound to canonical sorted/deduplicated exact policy, schema, owner and monotonic revision. Policy changes permanently invalidate Full until acknowledged again. Input reservations persist their permission binding; Full cannot elevate running/legacy inputs. Both paths recheck live service/entity capability outside the short shared admission/revocation gate, then recheck mode/policy/grant/input/revision and installation-wide uncertainty in it. They commit `dispatching`, recheck authorization at durable attempt admission and invoke one POST before releasing the gate, without holding it during HA waits. Permission changes invalidate pending/unattempted actions and abort transport promptly; attempted effects cannot be undone. Selecting Full never runs old Ask proposals. The tool is replay-unsafe; dispatching recovers to unknown and all Home writes stay blocked installation-wide until the specific owning human reconciles. Snapshots/SSE include owner-filtered permission state and receipt metadata. HTTP success means `accepted`, not verified device effect; interruption/error leaves unknown. Human resolution is a note, not an automatic retry.

**Code:** Pi coding-agent's genuine `read`, `bash`, `edit`, `write` factories. Controller constructs metadata but NEVER executes their host implementations. A bounded HMAC-authenticated Unix-socket adapter invokes them in the [separate confined worker](workspace.md). Code sessions select only that extension; older/Home sessions are explicitly kept HA-only. One trusted coding operator shares the worker's own workspace. Every coding tool is unsafe to replay. Unknown outcomes block further calls for that input; startup guards all interrupted Code turns against fresh model-driven reissue. A new human input—not duplicate admission retry—releases the guard.

## Native companion canvas (unreleased source)

Hearth is its own companion on genuine Pi Durable, not a Muse integration or a replacement chat-history wrapper. `ha_build_view` accepts only a bounded title, 1-4 named sections and at most8distinct exact configured entity IDs. The controller obtains selected HA state/attributes itself; model-provided values, HTML, URLs and actions are not accepted. All IDs are validated before any GET, and scope is rechecked before publication. A failed/partial read does not replace the previous view. Labels and readings are sanitized with the live secret collection at commit.

A latest-only conversation `HomeCanvas` and a task-scoped `CanvasReceipt` are written together through the real tool's `api.commit`. An interrupted pre-commit read may repeat safe GETs; post-commit recovery returns the receipt without rereading/reapplying an old canvas. Conversation creation/boot initializes absent documents for older sessions. The existing owner-bound snapshot/SSE projects the canvas through current exact scope; Code suppresses it and never selects the Home tool. A separate `watchDoc` publishes canvas-only commits. Old transcript history remains history: pruning the current canvas is not erasure of previously disclosed context.

The UI renders safe text nodes, source IDs and HA-read/commit times. Readings are **saved observations**, not sensor subscriptions or physical proof. Refresh/explain controls only draft an ordinary input for the human to send through the existing durable admission path. No new privileges, service dispatch, background polling, arbitrary model-generated DOM or external SDK/account. [Direction, demo and deferred capabilities](hearth-companion.md).

## Inference and authentication

Pinned Pi ModelRuntime receives explicit protected OAuth storage and no project/personal model/resource discovery. Static configured-provider auth metadata is initialized without remote catalog requests. Official `openai-codex` device/browser OAuth and locked refresh remain backend-only. Experimental Anthropic OAuth is gated by `HEARTH_ANTHROPIC_AUTH_ENABLED` (exact `true`, default off; typed HA option fallback) before credential/runtime/transport initialization. Native Pi browser/copy-code login uses a separate `0600` file and state-required owner-bound answers. The pinned MIT `pi-anthropic-auth` 3.4.2 transport helper alone is loaded with pinned jiti 2.7.0, filesystem caches/debug/discovery disabled; no extension factory/config/account diagnostics are loaded. Pi owns auth and the model catalog; compatibility applies only to OAuth requests. The provider-version rejection retry is a model-transport retry, never a tool/effect dispatch. `/login [configured-provider]` is intercepted outside durable admission/model context. The flag does not change the configured model or any HA/Code capability. Login state/callbacks are bounded, owner-bound, CSRF-protected, cancellable and outside model context. API-key mode is distinct; no provider key is copied to process environment by the adapter. Known current/refreshed secrets are filtered before durable input, model events, coding results and API output. This is not arbitrary secret detection.

All routes check actual Ingress peer/allowlisted ID or loopback Basic auth; session ownership applies to SSE/snapshots/actions. POST requires exact Origin and browser-bound CSRF. User/model/tool strings are text-rendered. OAuth secrets/options/database stay in controller `/data`, absent from the worker's filesystem/PID/network namespaces. No generic model/HTTP/HA proxy is exposed over worker IPC.

The App has only its own bridge `addon_config` mapping. A trusted external operator—not the App/model—creates the worker container with no network, zero caps, no-new-privileges, seccomp, enforcing AppArmor, readonly rootfs and resource limits. Worker startup verifies these invariants and fails closed. Actual target-system evidence, backup restoration, kernel security and mobile behavior are distinct from source tests: see [validation](validation.md) and [threat model](security.md).
