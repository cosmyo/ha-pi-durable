# Changelog

## 0.3.3 — shared household context

- Shared lists: Home Assistant to-do lists (for example a shopping list) appear under **Today → Lists** and in Home chats for every authorized owner. Adding, completing and reopening an item are low risk; renaming and removing are medium and always ask. Lists must be allowed explicitly in scoped mode (`allowed_entities` plus the `todo.*_item` services); a changed or missing item is refused before anything is sent, and an unknown outcome is never retried.
- Household memory: next to each owner's private memory, facts the household shares (approved through the usual suggestion flow, editable by any authorized owner, shown as "You" or "Another household member"). Home chats get them as a separate, delimited, non-authorizing HOUSEHOLD block; the risk judge never sees memory.

## 0.3.2 — decision-model risk judge

- Risk judge: `risk_judge_model: systemone/<model>` uses any Jev/SystemOne-compatible decision model (for example Jev, Clef or Clef-flash) at `risk_judge_url`: two typed questions (aligned yes/no, needing 90%; risk level, escalating only upward when the likeliest level or 20% of the probability is higher) instead of generated text; same private-address rules and fail-closed handling as `endpoint/<model>`.

## 0.3.1 — your profile, briefing summaries, code-improvement suggestions, Home World polish

See the App changelog for details. Also: the risk judge judges each requested change on its own; local judges are asked to answer without hidden thinking; measured on-host judge quality documented.

## 0.3.0 — Home companion preview: Claude-style UI, apps, Today, memory, Home World, automation troubleshooting and Admin access mode

- Admin access mode and action risk classifier (source slice): new App option `access_mode` (`scoped` default, `admin` opt-in; `HEARTH_ACCESS_MODE` for local development). Admin mode reads every entity/registry/config and allowlisted Supervisor info (directly over Supervisor's own REST API, see below), and adds proposal tools for any service call, automation/script/scene upsert/delete, allowlisted registry/helper mutations and allowlisted Supervisor actions; scoped mode is unchanged and has none of these tools. Every proposal (including app and Home World toggles) is classified low/medium/high/critical by deterministic rules recorded on the receipt; Full access auto-runs low, medium only with an agreeing judge; high/critical always ask and critical needs a typed confirmation. Optional cheap risk judge (`risk_judge_model`: `auto` = gpt-5.6-luna → claude-haiku-4-5 → off, `off`, `<provider>/<model>`, or `endpoint/<model>` with `risk_judge_url`/`risk_judge_api_key` for a private llama.cpp-style server) that may only escalate; short-lived judge sessions reuse provider prompt caches; failures fail closed. Approval cards show each action kind, a risk badge, the deciding rule and the judge note; Settings shows Access and Risk judge read-only. Security-review hardening: automation/script writes are always at least high (critical when any critical service is mentioned, templates/case included); scenes rated by member domains; covers by one live read of every target (missing/door/garage/gate → high); `update.*` on Core/OS/Supervisor/Hearth → critical; self-protection on every domain's targets; renames of sensitive entities → high; Supervisor info filtered to safe fields; judge replays at most 4 prior exchanges. Admin-mode Home World/app controls cover fans, climate, covers, media players, automations, input_boolean, humidifiers, vacuums and locks, each press risk-classified; admin entity reads return bounded, redacted attributes.
- Set up the Home World with Hearth (source slice): **image attachments** in Home chats (composer ＋ picker, client-side JPEG re-encode ≤2048 px, ≤4 images/message; server magic-byte type check for JPEG/PNG/WebP, HEIC and others refused, ≤4 MB and ≤4096 px each, ≤10 MB per message, ≤12 per chat) stored in the durable Pi user message as `ImageContent`, served back as thumbnails through an owner-checked `GET /api/sessions/<id>/images/<entry>/<n>` (snapshots carry references only; CSP `img-src 'self' blob:`), and refused with `model_no_image_input` for text-only models. **Bundled skills** (`hearth_pi/skills/<name>/SKILL.md`, packaged in the image): Home prompts list names/descriptions, `hearth_skill` returns one skill's text from the fixed set. The first skill, `home-world-setup`, covers reading a plan, mapping rooms to areas, one batch of clarifying questions, grid math, doors, outdoor and shed spaces and iteration, with a synthetic example. **Tools** `world_layout_get` (bounded, scope-respecting) and `world_layout_propose` (path-specific validation incl. overlaps, unknown/missing rooms, bounds, cols 16–40, ≤8 decor) store one per-owner draft (7-day expiry) next to the saved layout without changing it; `GET /api/world` reports it, `GET /api/world/draft` returns the preview, `POST /api/world/draft/keep` (revision-checked, same validation as saving) and `/discard`. Chat proposal card with **Open preview**; Home World preview banner with **Keep**/**Discard**; editor gets **Set up with Hearth…** (drafts only). The inputs route now accepts bodies up to 14 MB and the server request timeout is 60 s.
- ChatGPT/Codex and Anthropic subscription sign-in now survives a mid-conversation 401 without the owner re-authenticating by hand: every model call already refreshes a near-expiry OAuth token first (Pi's own five-minute window); a 401 despite a locally valid-looking token now refreshes once more and retries that one provider request once, strictly before any event of the turn (so before any tool call) reaches the rest of the app — never re-running a tool side effect. Concurrent turns on the same credential share one in-flight refresh (single-flight), the rotated token is persisted by the existing atomic, owner-only credential store, and a revoked refresh token still falls back to the existing sign-in-again failure. Tokens are never logged or returned.
- New **Hearth Judge** add-on (`hearth_judge/`, experimental, source slice): a second, independent App in this repository that serves a small open-weight model (`qwen3-1.7b-q4_0` default, `qwen3.5-2b-q4_0` A/B candidate — both a pinned Hugging Face repo/revision/file and a verified sha256 in `hearth_judge/models.json`) through the official `ghcr.io/ggml-org/llama.cpp` server image, pinned by digest, as a generic OpenAI-compatible `/v1/chat/completions` endpoint for Hearth Pi's optional risk judge. No `ports:`, ingress, `homeassistant_api` or `hassio_api`; reachable only on the internal `hassio` network. `run.sh` starts as root only to `chown` its `/data` subdirectories, drops to a non-root user via `gosu`, then downloads and sha256-verifies the configured model (refusing to start on any missing/unverifiable pin) before executing `llama-server` with a single slot (`-np 1`, not owner-configurable) and a cached static prompt prefix, with no Web UI. See [hearth_judge/DOCS.md](hearth_judge/DOCS.md). A new 60-case synthetic evaluation harness (`hearth_pi/eval/judge-cases.json`, `scripts/eval-judge.mjs`) scores any OpenAI-compatible judge endpoint (plus, best-effort, Hearth Pi's own signed-in cloud judges when local credentials exist) for accuracy, false-agree rate, escalation recall, JSON-parse failures and p50/p95 latency, and writes a Markdown report; see [hearth_pi/eval/README.md](hearth_pi/eval/README.md). The endpoint judge (`src/judge.ts`) is unchanged in shape (strict JSON schema, `temperature: 0`, small `max_tokens`) — only its expected-latency documentation grew for tiny local models; the cloud judge path is untouched.
- Fix: Supervisor access moved off Core's `supervisor/api` WebSocket proxy (verified against a real Home Assistant 2026.9 / current Supervisor install to fail with `{"code":"unauthorized"}`, since the Supervisor-proxied Core connection is not an HA admin user) onto Supervisor's own REST API (`http://supervisor/<path>`, `Authorization: Bearer $SUPERVISOR_TOKEN`). The manifest now grants the add-on's token Supervisor's `manager` role (`hassio_api: true`, `hassio_role: manager`) in every installation — never `admin` — which Supervisor's own role table covers for every endpoint Hearth allowlists; Hearth's fixed path allowlists and safe-field projections remain the actual enforcement boundary, re-checked immediately before every send. Every existing protection carries over (allowlists, safe-field projections, log redaction/16 KB tail, method pinning, self-protection/critical classification, bounded responses) and redirects are now refused outright. Mutations now distinguish a definite pre-handler 4xx — reported as a new **failed** receipt status, done and never retried — from a network error, timeout or 5xx that may have reached Supervisor's handler, which stays **unknown** and keeps blocking Home writes installation-wide until a human reconciles it (unchanged). Backup create/restore and add-on install/update ask Supervisor to queue a background job (`background: true`) instead of holding the request open for up to 600/900 seconds; a new `/jobs/info` and `/jobs/<job_id>` read lets the owner check progress. Scoped mode still never registers or calls a Supervisor tool, enforced in code independent of the token's role.
- Self-improving within the constraints, L3 code-level improvements (source slice): a bounded, durable, per-owner counter (`hearth.tool-failures`, 7-day rolling window) built only from the Harness's own Home-tool error results (tool name + error code, never prompt/response text) feeds a new `tool_health` prompt section that tells the model, in counts only, when the same tool has really failed with the same error code at least 5 times — the only trigger for a new Home-only tool `suggest_code_change(title, problem, proposal, evidence)`. It re-checks the claimed evidence against the real counter server-side (refusing a too-high count, an unseen pair, or title/problem/proposal containing a code fence or diff/patch marker) before filing a `code` suggestion kind in Today (strict schema: no field for code, a patch, permissions, scope, credentials or settings). A `code` suggestion naming a security-sensitive area (scope, approval, permission, credential, token, sandbox, CSP, sanitizer, risk, judge, supervisor) is labelled **Security review required** and gated behind opened details plus a typed `CONFIRM`, enforced server-side, never a one-tap action. Its only action besides Reject/Snooze is **Draft in Code session**, which creates a brand-new Code (workspace) session through the existing session machinery (refused with `workspace_not_enabled` when Code sessions are off) and submits one fixed template message holding the problem/proposal/evidence marked as untrusted data, asking the offline, confined worker for a patch, a unit test and a short PATCH SUMMARY. Hearth never applies anything from this flow: there is no self-apply path (a static test asserts it), and the owner reviews, downloads/copies the patch from that Code session and releases it normally, exactly like any other Code session.
- Self-improving within the constraints (L1/L2, source slice): **household memory** — a per-owner Pi Durable document of owner-approved facts/preferences (≤200 characters of plain single-line text each, ≤60 items; source "you" or "accepted suggestion" with its chat) managed in **Settings → Memory** (add, edit, forget). Home conversations receive it as a delimited `household_memory` prompt section marked OWNER-APPROVED CONTEXT that the system prompt says never grants permissions, widens scope or overrides safety rules; item text is escaped so it cannot close the section tag or forge the BEGIN/END markers; at most 4 KB is shared, trimming oldest-first with a warning. **Suggestions** — Home-only tools `suggest_memory(text, reason)` and `suggest_app_change(appId, baseVersion, patch, summary)` only file a proposal (app patches are validated exactly like `app_update` but never applied) into a new Suggestions section at the top of **Today** (no new drawer row) with Accept / Edit (memory text) / Reject / Snooze. Accepting is an Origin/CSRF-checked owner request bound to the proposal hash; an app change is applied through the shared `app_update` validation only if the app is still at `baseVersion`, otherwise it is kept as a visible conflict. The proposal schema has exactly two kinds (`memory`, `app_change`) — nothing can change Home permissions, entity/service scope, credentials, providers or settings (tested). Rejections are remembered for 60 days by normalized text or appId+patch hash; at most 3 suggestions per conversation and 10 per owner per rolling day, 20 pending. **Feedback loop** — after a 👎 with reasons in a chat that built or changed an app, the next owner turn in that chat sees an `owner_feedback` prompt section (ids/enums only) and may offer one `suggest_app_change`; the 👎 chips say "Hearth may suggest a fix". No background model run; the model-written briefing summary stays deferred for that reason.
- Home World v1 (iteration 3, world part): the prototype becomes a feature. The house is auto-generated from the Home Assistant areas of in-scope entities (new read-only registry access: the WebSocket allowlist adds only `config/area_registry/list`, `config/device_registry/list` and `config/entity_registry/list`, projected server-side to `allowed_entities` plus area/device names), with an "Unassigned" shed, deterministic room sizing/placement, furniture by area name and sprites by domain/device class. The everyday surface is the ambient strip above Home chats (chip; drops in while Hearth is thinking or on pull-down); the full-screen pixel house opens from it or Settings → Home World. Live controller-read values with as-of times, bounded refresh only while visible, anomaly glints (unavailable, open at night, low battery, leak), device card with Ask (draft only) and light/switch toggles through the existing Home permissions broker (Read-only disabled, Ask exact approval, Full scoped once). Think mode moves the character only for real `pi.live` tool calls naming a device; no frames while idle, paused when hidden, 30 fps cap, DPR ≤ 2, reduced motion → no walking. Per-owner customization (room names/positions/sizes/floor styles, device rooms, character, pet) is a Pi Durable document with optimistic concurrency and Reset to auto layout; a prototype localStorage layout is imported once and cleared. Accessible list view with the same actions. Removed the three.js diorama variant, the vendored three.js, the variant switcher and all prototype labels.
- Automation troubleshooting (read-only, use case #4): Home chats get `ha_automation_config`, `ha_automation_traces` (≤5 compact runs: trigger, conditions passed/failed, actions, errors, timestamps), `ha_automation_trace_detail` and `ha_automation_activity` (logbook ≤24 h plus history for ≤3 in-scope references) for automation entities in `allowed_entities`. Config via REST GET `config/automation/config/<id>` (latest-trace fallback); traces via a new minimal WebSocket client that can send only `auth`, `trace/list` and `trace/get` (bounded time/frames/commands, redacted). Referenced entities outside the read scope are named, not read, and run observations are withheld when any reference is out of scope. Credential-shaped values are scrubbed while `!secret` refs stay literal. The Home prompt now lets Hearth draft corrected YAML in a code block with paste instructions while stating it cannot apply it; it still has no configuration write path. Friendly transcript labels for the new tools.
- Proactive Home (iteration 2, source slice): a durable controller-side scheduler evaluates deterministic watchers — state transition, numeric threshold, duration in a state and daily/weekly local-time reminders — defined on apps (HAS/1 `watchers`, at most 6, validated with path-specific errors; the vocabulary has no action field) or created by the owner in a new **Briefings & watchers** sheet. It polls only exact in-scope entities about once a minute (at most 50 reads per pass), never calls services, never starts model input and imports no HA client or Home permissions broker (static closure test). Evaluation state and an idempotency ledger live in Pi Durable documents committed with each card, so restarts never duplicate a card and a schedule missed while Hearth was off is delivered once, marked late. Cards land in a new **Today** inbox (drawer row with unread badge; Dismiss, Snooze 1 h / tonight / tomorrow, Open app, Ask about this — drafts only) with controller-read values and as-of times. Owner-configurable morning/evening briefings (default off) read a chosen app or saved Home view at their time; missing or out-of-scope entities show Unavailable, never a guess. The optional model-written briefing summary is deferred. L0 feedback: 👍/👎 on assistant replies with fixed reason chips, stored as ids/enums/model label/time only (no prompt or reply text, schema test), shown on an Insights sheet with Export and Delete all. The L1/L2 Suggestions inbox is not included.
- Apps on demand v0: Home chats can build household mini-apps as declarative HAS/1 specs (flat element map, 15-component catalog, path-specific validation, scope/read-policy/service-scope checks) with `app_create`, `app_update` (JSON Patch + optimistic concurrency), `app_get`, `app_list` and `catalog_describe` (four templates). Specs are append-only Pi Durable versions with separate app-local state (checklists, counters, notes); revert appends a version. A trusted renderer shows controller-read values with as-of times and Unavailable states; ToggleAction presses go through the existing Home permissions broker (Read-only disabled, Ask exact approval, Full scoped once, unknown never retried) and AskButton only drafts. New Apps drawer row, full-screen app view, pinned apps on empty chats and transcript cards with Open/Pin and diff summaries. Session SSE now waits (bounded) for a slow reader to drain instead of closing on the first backpressure signal.
- ChatGPT/Codex and (flagged) Anthropic subscriptions can be signed in side by side over one Pi model runtime with separate private credential files. Auth routes take an optional `provider`, `GET /api/auth/providers` lists each provider's status and bootstrap reports `authProviders`. The session model picker adds signed-in providers' models (provider/model pairs); a not-signed-in provider's model is refused, and the offline demonstration is unchanged.

## 0.2.0 — subscription and isolated coding preview

- Matching exact Pi 1.0.1 pins; SDK 1.0.0 shrinkwrap advisory resolved without audit suppression.
- Official ChatGPT/Codex OAuth device login, state-required browser fallback, private serialized credentials/refresh and protected owner-bound UI.
- Genuine regular-Pi tools in a separate offline confined worker; explicit Home/Code sessions, no HA/model/host credentials in the worker.
